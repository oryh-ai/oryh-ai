# 初始化工作区

新工作区什么都没有。这一页讲往里装东西的顺序，以及每一块到底是干什么的。

其中绝大部分都可以让管理员的 agent 去做，而不是手点 —— `oryh-master-data` 导入产品、供应商和客户，`oryh-access-admin` 改谁能做什么，`oryh-policy` 写公司制度。控制台是你核对结果和处理例外的地方。

如果你更希望被人领着走，那也是一个技能：让管理员的 agent 初始化工作区，`oryh-workspace-setup` 会先读已经配好的部分，再问清楚这家公司到底做什么，然后把剩下的推完。之后它还回答另一半问题 —— 还缺什么没配。

## 人：两种不同的记录

这个区分每个人都会踩一次，所以先学它。

- **用户（user）** 是登录身份：一个邮箱、一个密码、一个角色。从不登录的人不需要它。
- **员工（employee）** 是人事档案：姓名、工号、单据所指的那个人。工时、假期余额、工资条都挂在它上面。

两者关联，但不是同一条记录，各自都可以单独存在。一个你要付钱但从不登录的外包，是有员工档案、没有用户。一个进来查审批历史的外部审计，是有用户、没有员工档案 —— 控制台会在待办页面直接这么告诉他，因为个人工作队列总得是关于某个人事记录的。

**邀请用户**在 *人员与权限 → 用户与邀请*。邀请是一条邮件链接。在 standalone 默认的 `ORYH_EMAIL_BACKEND=console` 下，邮件哪儿也没发 —— 整封信连同链接被打印到 API 日志：

```bash
docker compose logs api | grep -A6 "\oryh email\"
```

把那个链接按你们平时的方式交给本人。在邀请超过几个人之前，先把 SMTP 配好（见[安装部署](install.md)）。

**建员工档案**在 *人员与权限 → 员工档案*，或者让 agent 用 `oryh-master-data` 批量导入。

## 权限：角色与能力

在 *人员与权限 → 角色与权限*。

角色是一组具名的能力。能力是动词，有时还带对象类型的作用域 —— `timesheet.submit_own`、`payroll.read`、`purchase_order.manage`。一个人的 agent 能做的，恰好是这个人的角色授予的，一点不多：由凭据决定，而不是由 agent 自称是谁决定。

从工作区预置的角色开始，等真实工作提出要求了再加能力，不要一开始就铺满。最快的路径是对管理员的 agent 说一句话 —— 「让谢婷能下采购单」—— `oryh-access-admin` 会把它变成正确的授权。

设计权限方案之前，有两条规则值得先知道：

- **读也是权限。** `payroll.read` 和改工资一样重，所以有些能力**没有授予任何一个预置角色** —— 由谁持有是你的决定，不是默认值。
- **「我的」和「所有人的」是两种授权。** 每个人都能看自己的工时、请假、报销、采购申请、报价、订单、线索和商机，以及转到自己手上审批的单据。看**所有人的**需要 `timesheet.read_all`、`leave.read_all`、`expense.read_all`、`purchase.read_all`、`quotation.read_all`、`order.read_all` 或 `crm.read_all` —— 或者一份不可能闭着眼做的工作：能推进某类单据、发货、开票、付款的角色，本来就读得到它。希望销售管线全员可见的团队，把 `crm.read_all` 授给 `member` 即可；这是你的决定，不是默认值。
- **共享单据也按授权读。** 发票、收付款、采购订单、运单、库存、业务对象、往来账户没有「本人」，读它们各要一项读权限（`invoice.read`、`payment.read`、`purchase_order.read`、`shipment.read`、`inventory.read`、`business_object.read`、`billing_account.read`）。`member` 默认全都有，所以员工读得到公司的单据；写某一族的岗位读得到那一族，带作用域的授权只读它那个作用域（`invoice.manage:sales` 读销项发票，`business_object.write:warranty_card` 读保修卡）。给外部账号——供应商、客户的代表——建角色时，只给它需要的读和写：没有一族的读权限，它就只看得到自己经办、自己创建和转到自己手上的记录。
- **文字无法扩大授权。** 技能说明和 calibration 改变的是「怎么做」；「允许做什么」由服务端决定，不管指令里怎么写。正是这条边界，让改技能文字这件事可以随手做。

## 主数据

在各个主数据页面，或让 agent 用 `oryh-master-data` 批量导入：

| 页面 | 装什么 |
|---|---|
| 项目 | 工时和成本归集到哪儿 |
| 客户 | 零售和 B2B 共用一张表 |
| 供应商 | 你从谁那儿买 |
| 产品与 SKU | 你卖什么、存什么 —— 带分类树、按类型的图片,原材料也是产品(`raw_material` 类型) |
| 物料清单 | 一件成品由什么做成;每个产品一版生效配方,排产时展开算缺口 |
| 客户联系人、价格协议 | B2B 客户那边的人,以及你和他们按产品谈定的价 |
| 销售渠道、店铺、设施 | 在哪儿卖(渠道代码就是平台订单带来的键,店铺挂在渠道下)、从哪儿发货 |
| 资源 | 会议室、车辆、设备 —— 一切可预订的东西 |

只装第一批真实单据需要的。这套系统不要求你先做六个月主数据配置才肯收第一条记录。

## 公司制度

`oryh-policy` 把公司自己的规矩 —— 员工手册、报销制度、采购审批权限 —— 记成带版本的、已发布的文档。它们不是摆设：agent 在决策时会读，所以「每天报销上限 500」写成制度，是一条 agent 会执行的规则，而不是一段没人打开的文字。见[公司制度](https://github.com/AIE-enginehub/Oryh/blob/main/docs/policies.md)。

## 你自己的对象类型

在 *对象与规则 → 对象类型与流程*。内置单据覆盖了常见的那些；保修卡、现场勘查单、设备交接单则由你定义 —— 字段用 JSON schema，生命周期用状态机，词汇是你自己的。之后 `oryh-business-object` 就能像对待其他东西一样记录和查询它们。

这扇门前有两道闸，所有工作区都一样。服务端会拒绝用系统已有对象的名字建自定义对象 —— `customer`、`product`、`quote`、`sales_order`、`supplier` 之类 —— 并指回真正的页面。而 agent 在创建任何自定义对象之前必须先说清楚：叫什么、有多少条数据要进去、内置的哪个集合本可以装下；已有内置的"同类"时，它会向你要理由并记在类型定义上。历史客户和产品永远不是自定义对象 —— 它们进"客户""产品"页面，用批量导入。

## 历史数据

如果是从老系统迁过来，`oryh-data-migration` 就是干这个的 —— 成批的历史报价单、订单和发票，规模大到不可能靠点。
