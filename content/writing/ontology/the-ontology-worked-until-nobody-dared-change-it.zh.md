# 本体不是做不出来，是后来没人敢改了

*《当 Agent 开始操作企业》· 研发随笔*

想象一个本体项目的第一阶段：把汽车销售梳理得很漂亮。车、客户、订单、交付、门店都有了对象和关系。演示时点开一辆车，销售记录一路能追到负责人。有人说，这次终于把业务讲清楚了。

第二阶段，售后要追单条轮胎；第三阶段，质保要区分客户自带配件；再后来，财务说“销售完成”和“收入确认”根本不是一个时间点。每个要求都合理，也都值得做。只是那张原本清爽的图，改起来越来越像一项工程。

这是一种可能发生的过程，不是某个真实客户项目的复盘。它要问的是：本体最后为什么会被放在一边？未必是没人会建，很多时候是建出来之后，维护它越来越难。

## 最初顺手，后来每改一次都要开会

“把轮胎单独建成对象”刚说出口，售后觉得是小改。数据团队问旧维修记录怎么迁；开发问原来查整车质保的接口谁来改；客服问已经发出的“在保”承诺算不算；财务问报表历史口径要不要重算。业务负责人忙着处理今天的工单，不一定有空替一张模型协调这些事。

没有谁故意拖延。只是每个人承担的风险不同。数据团队怕造出假的历史，开发怕旧页面悄悄错，客服怕答复客户前后矛盾，管理层怕改完以后没人说得清指标为什么变了。要把所有人拉齐，成本就不再是“加一个对象”。

如果公司频繁调整商品、合同、渠道和审批，类似的会越来越多。第一回大家认真开，第二回试着缩短评审，第三回有人说：“这次先写在备注里吧，不影响主流程。”这句话往往不是懒，是大家算过账以后做出的现实选择。

备注开始多起来，模型就开始少知道一点业务。偏偏旧对象和旧关系仍然在系统里，看起来很正式。Agent 如果只读本体，会漏掉备注里的新做法；如果每次还得读备注、邮件和原始单据，那最初宣称“本体是企业 AI 唯一理解层”的理由就弱了。

## 绕开一次，会让下一次更容易绕开

一开始只是一次临时处理：新质保例外来不及改模型，客服先在工单里写明。下一次类似申请，另一个人照着上次备注办。再下次，团队做了张共享表，专门列“本体尚未覆盖的情况”。表里记录得可能很认真，却没有进入图。

于是出现两套现实。图里是统一定义过的业务，表格里是最近真的发生的业务。项目报告仍能说本体覆盖了车、轮胎、订单和质保；做事的人却知道，决定能不能赔还得看一眼表格。越依赖旁路，本体越不完整；越不完整，大家越不敢只改本体就上线。

这是一个很普通的组织循环，不是什么神秘的技术崩溃。软件还在，数据也还在。只是最费判断的那些新情况，逐渐迁移到了模型外。某天来查图的人以为自己看到了全貌，反而比知道“这里还有一张表”的人更容易做错决定。

我会特别注意几个信号：新的业务要求有多少被放进备注；模型变更从提出到可用要等多久；一次变更需要多少部门签字；旧对象里有多少字段已经无人解释；Agent 作决定时到底读的是图，还是总要另外找人问。比对象数量、关系数量更能说明系统是否还活着的，是它能不能接住下一次变化。

## “谁负责维护”不是一个可以跳过的问题

模型的维护权听起来可以指定给一个团队，实际却常常跨边界。建模的人懂结构，但未必知道合同里的“交付”在这个月改了定义；一线人员懂客户情况，却未必知道改一条关系会影响十张报表；开发知道接口依赖，不能代替财务决定旧收入要不要重算。

让 AI 帮忙也没法把责任蒸发。AI 可以从新制度中找变化、列出可能受影响的对象和流程，甚至写好迁移建议。最后仍需要有人确认新意思、决定追不追旧单、接受迁移结果。若把这些确认步骤省掉，省的是审批时间，增加的是一张没人敢信的地图。

也不是所有本体都会走到这一步。一份范围很窄、边界稳定的对象目录，或一组有来源的客户与合同关联，可能维护得很好。问题出在把它抬成企业运行的完整“镜像”，再让所有决策先经过它。镜像越大，维护责任越散；责任越散，每个人越倾向于先别动。

真想判断一张图该不该继续养，不妨给它做一次很朴素的盘点：过去三个月新增的业务说法，有多少已经进图？没进去的由谁记着？有人指出图错了，平均多久能改好？能回答这些问题，说明团队还在主动维护；答不上来，却继续要求 Agent “以本体为准”，就等于要求它相信一张没人负责更新的地图。

## 把“还不知道”留在台面上

不妨换一个出发点。软件把发生过的交易、审批、维修和付款记准，保存原始材料、时间、版本和证据。硬约束——金额合计、权限、不能重复出库——写在代码里。Agent 读当前问题所需的记录和制度，判断下一步；制度没写清、旧材料不够，就把缺口说给人听。

这里仍然会用到结构、索引和关联。只是它们可以是局部的、可修订的，能指回事实，而不是一份必须永远领先于业务的总图。需要追单条轮胎，就在那条业务线上认真记录轮胎；其他业务不必为了“全企业统一颗粒度”跟着拆到螺丝。

这样也不会自动消除维护工作。Agent 的操作说明要改，检索可能找错文档，旧事实仍需要人工确认。不同的是，企业改一条做法时，不必先判断自己有没有资格改动整幅图。新事实先能被诚实记录，新判断先能被解释和复核，然后再看哪些结构值得固化。

做 Oryh 时，我们就吃过旁路记录的亏：Agent 把客户、商品和单据导入了通用对象，专门的客户库和商品库仍是空的。后来我们拦住明确的名称冲突，让 Agent 遇到近似类型先检查现有结构并请人确认。这件事让我不太想再听“有一张完整的业务图就好了”。图可以帮忙找路，记录身份与事实必须守住，而业务的新说法要能被 Agent 读到、被人确认。否则图还在，却已经不是大家真正走的路。
