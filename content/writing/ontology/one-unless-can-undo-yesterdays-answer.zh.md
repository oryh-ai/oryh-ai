# 制度多了一个“除非”，昨天的审批怎么办？

*《当 Agent 开始操作企业》· 研发随笔*

设想一家汽车售后公司，初版制度很直白：整车购买不满两年，轮胎损坏可以按质保受理。系统因此给一批维修申请标了“在保”，有的已经生成待办，甚至有人已经批准了免费更换。

后来客服和维修部门把情况讲细了：单条轮胎可以独立索赔，除非此前更换的是客户自带配件。制度只多了一个“除非”，可接下来的问题一点也不小。

这个汽车场景是虚构的。我们关心的不是某条质保制度怎样写才对，而是一条新规则如何影响已经做出的判断。

## 新规则不是给旧表添一列

先别急着重跑所有数据。要问的第一件事是：新制度从什么时候生效？它只管新申请，还是也管尚未处理完的旧申请？已经批准、还没出库的轮胎，需不需要重新审？已经装到车上的，能不能也被系统改成“不在保”？

这些答案不是技术系统能替公司宣布的。它们牵涉客户承诺、责任归属和谁有权改变既有决定。把轮胎拆成对象，只解决了“系统能表示什么”；把例外写进规则，才开始触碰“旧决定怎么办”。

还得区分“制度今天发布”和“制度规定从哪天适用”。人事或财务有时会补发一份文件，说明上月某类申请就应按新口径处理；有时则明写下周一才生效。Agent 今天读到最新版，不代表它可以拿最新版覆盖昨天每一笔决定。查询时至少要知道申请发生日、判断发生日，以及所用制度的适用范围。

同一个申请至少有四层东西要分开：当时掌握的事实，当时有效的制度，当时据此做出的判断，以及后来实际执行的动作。今天发现客户自带过轮胎，是新事实；今天新发一版制度，是新规则；撤销一个待办，是新操作。别把四件事都塞进一个“当前质保状态”字段。

否则用户点开旧申请，只看到红色的“过保”，会以为两个月前客服违反了制度。事实上客服可能按当时的规则办得完全正确。后来规则改变，不会自动把过去的行为变成违规。

## 推理能多知道一条，不等于能撤回一条

这里还有一个技术上的错觉。把“车辆购买未满两年”与“轮胎在保”连成推理关系，前期很好用。后来补一句“客户自带配件除外”，有人以为把新条件加进去，旧结论就自然消失。

事情没那么简单。以 [W3C 的 RDF 1.1 语义](https://www.w3.org/TR/rdf11-mt/)作一个有界对照：它讨论的蕴涵关系是单调的，增加信息不会自动取消原来由较弱前提推出的结论。业务上的“除非”则可能要求重新判断、让旧结论失效，甚至撤销还没执行的动作。

这不是说所有本体系统都不能处理例外。可以用规则版本、有效期、状态迁移和专门的撤回机制，也可以把旧结论作为历史记录保留，再给当前处理另算一个新结论。问题恰恰是：每个例外的适用范围、追溯范围和后果，都得有人说清楚、有人接上，不能只靠“再加一条边”。

有些例外更绕。客户自带的是轮胎，轮毂还是公司提供的；服务顾问当时没记清；客户提供了购买凭证但无法确认安装日期。系统能算出“无证据证明在保”，不等于能算出“确认不在保”。Agent 如果要发起拒赔，应当把缺的证据和适用条款说出来，让人有机会核对。

## 已经发生的动作不会自动倒带

规则修改最容易漏的是执行后果。一个待办可以取消，一个审批记录不该抹掉，已经出库的轮胎更不能因规则更新而“自动入库”。如果新政策决定追溯复核，那也是一项新的业务行动：谁发起、谁通知客户、是否要求补证、是否允许维持原决定，都需要留下记录。

因此我更想看到的是一条时间线，而不是一个永远覆盖旧值的“在保”标签。时间线上写：申请何时提交，Agent 当时读了哪版制度、引用了哪些工单，谁批准了什么，何时产生新规则，新规则要求不要求复核，复核之后作出了什么新决定。

这样一来，今天需要判断下一步的 Agent 可以读到完整经过。它能说：“这单当时按旧制度批准，但尚未出库；新制度要求未执行的申请重新核对配件来源。”或者说：“新制度只对今日以后申请生效，旧决定保持。”这两句话都可能合理，前提是公司真的定过范围，而不是系统替人猜。

软件在这里负责保存规则版本、审批事实、待办、出入库和操作人；金额合计、权限和重复操作这样的硬约束仍要由代码守住。Agent 负责把当前有效的规则与这张申请的事实联系起来，解释为什么建议推进、暂停或复核。碰到制度没有说清的追溯问题，应该停下来问。

尤其是排队中的待办。已经发给仓库的“免费换胎”任务，不能因为一个夜间定时任务重算状态就静悄悄消失。至少要留一条取消或暂停的记录，告诉执行人是哪一版规则引发了变化，之前的审批谁做的，接下来等谁确认。否则自动化表面上保持了最新口径，现场却只看见一项工作莫名其妙不见了。

## 改一句话，别悄悄改掉整份制度

我们还得承认，Agent 本身也会把“除非”加错。一次实际开发反馈里，管理员只说“加个条件”，Agent 却把整份现行工作流定义替换成只含新条件的短文档。服务端保存了版本，没有丢旧文件，但下次执行的 Agent 读到的是不完整的新规则。后来我们要求先读现行全文，列明新增、改动、删除；出现用户没要求的删除，就先请人确认。

这个教训和本体没有直接的技术关系，却说明了为什么“版本”两个字不能只是界面上的标签。无论把制度做成图、规则表，还是自然语言，改动范围都必须可见，旧判断都要能解释，已经执行的动作都要能追到。想靠一个“最新状态”把过去盖住，迟早会碰到有人问：“当时到底按什么办的？”

做 Oryh 时，我们宁愿把规则的理解和推进留给 Agent，也不让它悄悄替公司决定追溯范围。软件记住旧事实和新事实，Agent 对照版本解释当下该怎么办。一个“除非”有时足以改变下一步，但它不该把昨天发生的事从账上擦掉。
