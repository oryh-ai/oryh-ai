# 轮胎今天成了对象，昨天上线的系统谁来收拾？

*《当 Agent 开始操作企业》· 研发随笔*

想象一家卖车、也做售后的公司。系统里原先只有汽车对象，轮胎规格是汽车的一个属性。按整车购买日期判断质保，售后界面显示“在保”或“过保”。用了半年，业务提出新要求：单条轮胎也要追生产批次、更换时间和索赔记录。

这只是一个假设场景。可它把一个常被轻轻带过的问题摆出来了：本体当然可以改。问题是，模型已经被系统使用以后，“改”到底意味着什么？

## 改图上的一个框，先要找到图下的线

“轮胎”从属性变成对象，看起来只是在图上多画一个方框。真正动手时，第一件事是给轮胎一个稳定身份。用出厂序列号，还是企业自己生成编号？没有序列号的旧轮胎怎么办？同一条轮胎从一辆车拆下装到另一辆车，身份不能跟着车重建。

接下来是关系。原来的汽车记录写着“轮胎规格 225/45R17”，新模型要写“这辆车在某段时间安装了这四条轮胎”。从一种字符串变成四个对象和四段装卸事件，不是字段改名。原字段还要不要留？保留的话，谁负责保证它和新对象一致？不保留的话，旧页面和报表去哪读规格？

售后动作也要改。之前“申请质保”可能只接收汽车 ID，再看整车购车日期。现在它要指明是哪条轮胎，查这条轮胎的批次、安装时间和更换来源。页面上的“在保”也变得含糊：是整车在保、某条轮胎在保，还是当前申请的故障在保？

权限同样会冒出来。原来售后人员可以改汽车的维修备注；现在谁能确认轮胎身份，谁能改安装记录，谁能撤销错误关联？财务报表、仓库出库、外部接口，以及 Agent 使用的工具说明，也可能读的是旧边界。

这些东西不是一张图画出来的，但一张图改了，它们就都来敲门。

还有上线当天的细节。新旧两套入口可能同时存在：门店 A 用新版售后页，门店 B 还在用旧接口；一个 Agent 已经按单条轮胎查，另一个仍按整车查。团队可以安排一段并行期，却得说明新记录写哪里、旧入口还能不能写、同一申请被两边处理时哪个结果作准。否则“逐步上线”只是把两套口径同时开放。

## 不是每次加字段都这样

批评本体时，不能假装“增加一个属性”必然让全公司停工。很多变更可以兼容地加进去。成熟平台也有迁移机制。比如 [Palantir 的公开文档](https://www.palantir.com/docs/foundry/object-edits/schema-migrations)明确列出哪些对象类型变更会破坏既有使用，包括主键、数据源或属性类型的变更，并提供相应迁移选项。

这说明技术上不是“不能改”。它也提醒我们：迁移不是把“更新模型”四个字写在任务单上就结束。平台能搬动某些编辑值，不会替企业回答一条没有序列号的旧轮胎是哪一条，也不会替售后决定旧的“整车在保”判定该如何解释。

真正危险的是改对象身份、拆分对象、改变规则含义这些事。它们要求团队同时处理两类问题：数据怎么搬，原来的判断还算不算。前者需要工程，后者需要业务负责人愿意签字。很多项目只盯着前者，直到旧报表给出与新售后页面不同的结论。

我们可以把新轮胎对象设为只对新记录生效，让旧车继续用旧结构。这是合理选择，但要明确地告诉每个查询者：同一个“质保状态”字段在不同历史区间含义不同。也可以逐辆补录旧车。那又要问证据在哪、人工核对谁做、补不出的怎么办。不存在一句“全量迁移”就把这些问题抹平的魔法。

即使回滚也不是按一个按钮。新系统如果已经记录了某条轮胎从 A 车拆下、装到 B 车，退回旧模型后，这两次动作要保存在哪里？若已经按新规则批准了一笔单胎索赔，再把规则恢复为整车规则，审批记录不能跟着消失。模型版本能回退，真实发生过的操作不能倒带。迁移方案里如果没有“新事实如何保留”和“旧系统如何继续读”的答案，回滚计划就还没写完。

## 最贵的是看不见的使用者

建模者通常知道自己改了什么，却未必知道谁在依赖旧含义。某个客服页面把“在保”用作筛选条件；一份月报按整车数量计算在保比例；一个 Agent 的操作说明写着“先查询汽车质保状态，再创建索赔单”。这些地方可能没有显式报错，仍然跑得很顺，只是答案开始变了。

这是比接口报错更难受的情况。报错会逼人处理，意思变了却不报警。于是更新本体之后，团队还要做依赖清点、旧新并行核对、典型案例回放，确认用户看到的结论没有悄悄换口径。

回放不能只挑“标准车、四条原装胎”。还要挑换过两次胎、只留了纸质凭证、索赔已经批准但尚未出库的单子。用新旧两套读法分别得出答案，差异逐条交给业务人看。差异不一定都是程序错误；有些意味着旧规则本来就粗，有些意味着新记录还不够。把两者混在一张“迁移成功率”报表里，测试通过了也不知道业务有没有通过。

如果本体只是帮助查询轮胎相关资料，修它的成本相对可控。如果它被放在所有判断的正中央，任何颗粒度变化都可能影响许多下游。模型越被称作“统一真相”，变更时越难找到一个小范围先试。

这也是为什么我更愿意让软件保存那些不该丢的事实：汽车、订单、维修单、轮胎出入库、版本和谁确认了什么。Agent 读当前有效的售后说明，联系这些事实判断下一步。某项判断需要精确到单条轮胎，却没有对应记录，就明确说缺材料，别用一条老的整车属性冒充答案。

做 Oryh 时，我们遇到过另一种“图上的一条线不够用”：十张付款单对应银行流水里的一笔汇总扣款。原先只支持一条流水关联一张付款单，后来我们增加按付款批次关联，同时让代码校验收支方向和金额合计。这个改动没有要求 Agent 决定数学上是否相等，也没有把十笔付款揉成一笔；它改的是记录能表达的事实。轮胎案例虽然是虚构的，提醒却一样：结构可以改，但每一次改动都要算清已经依赖旧结构的人和记录。
