# 知识图谱连了万条边，也读不懂一句人话

*《当 Agent 开始操作企业》· 研发随笔*

这些年讲企业 AI，常能听到一条熟悉的路线：先定义本体，再把企业资料做成知识图谱。客户是谁，订单属于谁，谁负责项目，谁能批准采购，都连成点和边。以后要回答问题，沿着图走就行。

图一画出来，很像脑子里的知识网络。也正是这个画面，让人容易误以为系统已经理解了企业。

但线能连上，和话能听懂，是两回事。

## 过去为什么非要把知识画成图？

传统程序擅长查找、计算和按条件执行，却不能像人一样读一份会议纪要，再领会一句“这次先让项目经理看一下，采购最终还得财务确认”在当前业务中是什么意思。

要让程序参与，先得有人把材料翻译成它能处理的形式：项目经理是个实体，项目和采购单之间有关系，审批人有某种角色，动作要满足某些条件。本体负责定义概念和关系，知识图谱把具体人、单据和关系装进去。

以常见的 RDF 图为例，[W3C 的定义](https://www.w3.org/TR/rdf11-concepts/)是由“主语—谓语—宾语”三元组组成的图。程序可以据此查询和遍历。它回答的是“数据里写了哪些连接”，至于连接在一项具体业务里意味着什么，仍取决于人当初怎么建模、怎么填数据，以及程序怎么用查询结果。

以前值得花力气做这层翻译，因为不翻译，许多程序就没法处理人的知识。今天我们得重新问：Agent 已经能读会议纪要和制度原文，还要不要先把它们全部改写成点、边和预设规则？

## 连到了项目，不等于拿到了审批权

假设一张采购单属于项目 P，项目经理是小周。图上很容易画出两条边：小周负责 P，采购单属于 P。查询一跑，就找到了小周。

此时系统可能给出一个很顺的答案：“这张采购单该由小周审批。”

可公司真正的说法可能是：“项目经理先确认用途；超过五万元由财务负责人批准；项目经理不在岗时由当周指定的人代看，代看不能代批。”

小周与采购单的连接没有错。错的是把“能找到相关的人”推进成“这个人有权作最终决定”。图谱沿边走了一步，看上去像是在推理，实际上那条从关联到授权的跳跃，是别人提前写进查询或规则里的。

当然，可以继续加边：谁有审批权、金额阈值、代理关系、生效日期、例外情况。再加下去，原来一句人能读懂的制度，慢慢变成一套需要不断改动的模型和规则。总会有下一句没有被放进去，比如“这次先看一下，但不要批”。

这不是知识图谱的语法缺陷。它可以表达复杂信息。问题是把它当成理解层以后，企业要为每个可能影响判断的含义，提前决定怎么表达、怎么更新、由谁维护。

## “系统知道”常常只是输出像知道

我们对知识图谱最警惕的一点，是它太容易产出漂亮的答案。

有人问“这个采购找谁”，程序查到了项目经理；有人问“这个客户买过什么”，程序沿着客户、订单、商品一路查过去。界面再把结果整理成一句自然的话，读起来就像系统懂了业务。

可是处理器并没有因为查到几条边，就突然理解“负责”“确认”“批准”之间的差别。它执行了人写好的表示和操作。输出可能有用，也可能正确；但结果流畅，不能反过来证明背后的知识表达完整。

这种错觉一旦进入企业决策，就会很麻烦。一个漏掉“最终还得财务确认”的模型，也许照样能返回审批人、展示流程图、生成待办。所有东西都正常运行，除了决定本身。

更难的是，使用者未必知道漏掉了什么。原始会议纪要和制度被放在图谱背后，屏幕上只剩一个看起来权威的结论。判断错了，要先追查是谁把哪句话翻译成了哪条边，才能知道问题从哪里开始。

## Agent 能直接读，也得对照事实

AI 带来的变化很实在：Agent 可以直接读“先确认用途，超过五万元由财务批准”，再看采购金额、项目归属、当前人员安排，解释下一步为什么找谁。公司补一句“代看不能代批”，这句话不必先等人发明一个新的关系类型，Agent 才能考虑它。

这并不意味着它读一次就必然读对。它可能漏掉“超过”，混淆代看和代批，也可能查错项目。我们的做法必须让它指出依据：看的是哪一版制度、哪张采购单、哪个金额；有冲突就停下来问。真正执行时，权限、金额计算和防重复写入仍由代码守住。

这份谨慎不是空想。我们遇过管理员只说“加个条件”，Agent 却把整份有效流程定义改写成只剩新增条件的短文档。旧版本仍在，但下一次执行的人读到的规则已经缺了一大截。后来我们把修订步骤改成先读现行全文，明确列出新增、修改和删除；出现用户没要求的删除，就停下来确认。能直接读人话的 Agent 也会犯错，所以原文、版本和改动范围都得留得住、看得见。

知识图谱也可以继续有用。人和单据的稳定关联可以帮 Agent 快速找到材料，图查询适合回答明确的结构化问题。经过确认的身份映射、带来源的关系，都值得保存。我们反对的是把图谱当成 AI 必须先吃下去的一份“企业知识翻译稿”，再让原文退到幕后。

因为这会重演传统软件的老路径：先把企业语言翻译成机器格式，再让机器按格式输出答案。换了图结构，翻译的工作量和误差仍由企业承担。

## 把知识还给说话的人

这里的分工其实很朴素。软件记下谁说了什么、什么时候生效，哪张单据发生了什么；可以索引、查询、核对确定的数量关系。Agent 读这些记录和人写下的规则，判断当前情形属于哪一种，必要时请人确认。它的判断也要留下依据，以便后来追问和纠正。

我们不需要先把“项目经理先看、财务最终批准”拆成一串关系和规则，才允许系统开始帮忙。今天真正缺的，往往是原话能不能找到、事实准不准、Agent 知不知道自己什么时候不能拍板。

知识图谱可以帮我们找路，但路不是目的地。本体可以帮我们命名，但名字不是理解。做 Oryh，我们更想让软件守住记录，让 Agent 带着人的原话和可核对的事实去判断；它拿不准，就把问题交还给人，而不是沿着一条看似完整的路径继续走。
