# 面向对象都没玩明白，怎么敢把企业交给本体？

*《当 Agent 开始操作企业》· 研发随笔*

聊企业 AI，总有人说：先建本体。把客户、订单、商品、部门、审批动作都定义好，再让 Agent 在上面工作。听起来很稳，仿佛只要对象和关系足够完整，AI 就不会乱跑。

我每次听到这里，都会想起面向对象编程。

不是说本体就是面向对象，也不是说不会写类的人就没有资格讨论本体。这个类比想问的是另一件事：我们真的有那么擅长预先划分世界吗？

## 写了 class，就算面向对象了吗？

学过一点编程的人都见过这种代码：把原来的一组函数放进 `OrderManager`，把共享变量改成成员变量，外面再套一个 `class`。语法是面向对象，程序还是按一条长流程往下跑。需求一变，继续在类里加分支。

这未必是程序员不够努力。订单到底负责什么、付款和订单怎样分工、一个概念该不该有独立身份，本来就难。业务每天还会给出新答案。类名写得漂亮，并不说明边界已经想明白。

我们在软件行业见过太多这样的争论：这个东西应该是属性，还是单独的对象？属于订单，还是属于履约？先继承，再组合，最后发现双方都没说清业务事实。

本体把问题放大到了整个企业。[本体管理工具](https://www.palantir.com/docs/foundry/ontology-manager/overview)可以配置对象类型、属性、关系和动作；但工具不会替企业回答：什么叫“有效客户”？试单算不算合作？哪个部门的“已完成”才是财务认可的完成？

一家企业内部，销售、仓库、财务给出的答案都可能不同。请谁拍板？下次做法变了，谁发现原来的定义已经不适用？这些才是建本体时最费人的部分。

我没有一份统计报告能证明“大多数程序员不懂面向对象”或者“大多数公司建不好本体”。但从这个类比出发，我们很难相信：连软件里一个对象的边界都经常争不清，换成整个企业，就能靠一轮建模把边界划准。

## 错误的模型，会让错误显得很正式

我们自己就碰过这样的事。一次历史数据导入，Agent 把客户、商品、报价单、销售订单都写进了通用对象。数据有了，系统原本的客户库、商品库和订单却还是空的。它甚至把新类型直接叫作 `customer` 和 `product`。

这不是复杂的哲学争论。连“这批数据里的 product，是否就是系统现有的商品”都没先确认，导入就已经开始。后来我们让服务端拦下明确的名称冲突；遇到意思相近、名字不同的情况，让 Agent 查已有类型、解释判断，再请人确认。

这个修补没有神奇地解决所有语义问题。它只是承认：有些边界可以由代码守住，有些边界必须看材料、问当事人。不能因为界面上允许建对象，就以为建出的每个对象都有了正确含义。

如果把这样的对象再往上连关系、配动作、交给 Agent 执行，错误会显得越来越正式。最初只是“好像同一种商品”，最后可能变成“系统认定是同一种商品”。一个未经核实的判断被做成了基础设施，后来的人反而更难发现它。

## 为什么旧软件总想先画好世界？

过去，这种做法有非常现实的理由。

程序要自己执行判断，就得事先知道字段代表什么，哪些值可以取，条件满足后走哪条分支。计算机处理器不会读一封邮件，就临时理解客户到底是取消订单，还是只想推迟发货。于是人先把业务翻译成数据结构、状态和规则，程序再照着执行。

本体是这条路上更有野心的一步：不只整理单个系统的字段，还想整理整个企业的对象、关系和动作。它解决过真实问题；对于需要统一口径、快速查询和跨系统联动的工作，也可能很有用。

但现在，Agent 可以直接读邮件、合同和公司的文字要求，联系具体记录来判断。它会犯错，也需要证据和校验；可它已经不必等所有业务含义先被人翻译成固定类型和分支，才有能力开始工作。

这对原来大量靠预设规则推进业务的软件，是一次根本性的挑战。我们说 AI 正在淘汰它们，指的是那种把企业做法预先写进程序、每次变化都要改程序的方式。CPU 仍然要计算金额、保存记录、执行权限检查；AI 系统自己也离不开计算机。消失的不是处理器，是“只能让处理器预先理解业务”的设计前提。

如果今天先要求企业把整个业务建成本体，再让 Agent 按预定义的动作办事，很容易把企业带回熟悉的流程：先访谈、再统一术语、再画模型、再做映射、再改模型。管理方式先迁就软件，软件才能上线。

这正是我们想从传统 ERP 里走出来的地方。

## 别让“懂业务”又变成一门配置工作

这件事之后，我们更在意一条分工：软件负责记录，Agent 负责逻辑。

订单是谁的、有哪些明细、收到了多少货、谁在什么时候批准过，这些要记清楚。订单明细合计、权限、防重复写入等确定的约束，要由代码守住。记录之间当然需要引用和关联，Agent 不可能凭空办业务。

但某家公司说“急单可以先找采购经理确认，非急单要等完整报价”，这不该再变成一套新对象、一组动作类型，或者客户专用程序。保存这句话及其适用范围，让 Agent 读相关订单、报价和当前规则，解释准备怎么做；说不清什么叫急单，就问制定规则的人。

别把这理解成 Agent 天生就懂企业。我们自己就遇过 Agent 把业务数据写错位置。让它负责逻辑，意味着还要给它找到事实的办法、读规则的办法、写回判断依据的地方，以及遇到歧义时停下来的习惯。

建一层本体，也不会自动免除这些工作。有人仍要决定类型是什么意思、数据从哪来、动作什么时候能执行。把这些判断藏进一层模型，团队可能只会更晚看见争议。

## 要不要给本体留一个位置？

当然可以留。经过确认的术语表、稳定的关联、指回原始资料的索引，都是有用的。特定行业里边界清楚、长期稳定的概念，也可以认真建模。

但我反对把“先完成企业本体”设为企业 AI 的入场券。企业本身没有一个等着被一次性画完的标准答案。让人为了给 Agent 用，先替 Agent 把公司所有说不清的地方说清楚，这个门槛太高，也放错了位置。

我们宁愿先把发生过的事记准，把原话留下，让 Agent 带着问题去读、去核实、去请求确认。每次判断都可以回看依据，发现不对就改规则、补记录、修工具。企业不必等一幅“完整的自己”画像画好，才能开始使用 AI。

面向对象的语法并没有自动带来好的设计。本体的对象、关系和动作，也不会自动带来对企业的理解。既然 Agent 已经能读企业自己的话，为什么还要把“先把企业翻译给机器”当作第一步？这正是我们做 Oryh 时反复追问的问题：让软件记住发生过什么，让 Agent 带着事实和人的原话去判断接下来怎么办。
