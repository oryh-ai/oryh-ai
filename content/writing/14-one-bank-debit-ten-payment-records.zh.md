# 银行扣了一笔钱，系统里却有十张付款单

*《当 Agent 开始操作企业：ORYH 的设计探索》· 第十四篇*

比如给十个人发工资，系统里每人一张付款单，银行流水上却可能只有一笔汇总支出。供应商批量付款，也会遇到同样的情况。

我们最初的付款关联只能指向一张单。拿这笔流水去关联其中一人，解释不了其余九笔；一直留在待对账列表里，也不是因为钱没付出去，而是记录结构说不清这件事。

这个问题提醒了我们：软件负责记录，首先得装得下实际发生的事情。不能让 Agent 为了适应接口，把银行的一笔扣款想象成十笔。

## 先把“一笔对一批”记下来

这些付款原本就可以共用一个批次参考号。我们让银行流水也能关联这个参考号，表示它对应整批付款。每个人的付款单仍然保留，银行那一行也还是一行。

为此，我们没有再造一套批次审批流程。需要补的是记录之间的关系，怎样找出关系、何时确认、出现差异怎么办，仍然由 Agent 推进。

代码负责几件确定的检查：这个批次必须存在，里面每笔付款的方向都要与银行流水一致，合计金额要对上。同一行不能既关联单笔付款，又关联整批付款。

测试里用了三笔简化金额：300、200、150，合计 650。对应 650 的支出可以关联；对应 640 的支出就被拒绝，返回三笔付款、合计 650、相差 10 的信息。把同样一批支出关联到收入流水，也会被拒绝。

我们希望错误信息能让下一步工作继续，而不只是留一句“匹配失败”。

## 用户不必知道批次号叫什么

接口能表达以后，Agent 还需要知道怎么用。

用户很可能只说：“这笔是工资。”他未必记得批次号，更不应该先学会字段名，才能让 Agent 对账。

后来我们补了两边的 Skill。登记工资付款的 Agent 统一记录批次参考号，并在回读结果时说明。负责对账的 Agent 没拿到批次号，也可以先查这笔扣款日期附近、已登记为付款完成的记录，按参考号分组汇总，提出候选。

它应该把话说到业务上：“这批有几笔，合计多少，日期和说明是否相符，准备关联到哪一笔银行支出。”人确认后，再保存关联。

金额相等在这里是查找线索和必要校验，不是业务事实的全部证据。如果两批金额恰好一样，还得看回单、日期和付款明细。Agent 负责逻辑，也就包括知道什么时候还不能作决定。

## 差额要解释，不能抹掉

少了 10 元，可能选错了批次，可能记录不全，也可能有退回或费用。软件不负责猜是哪一种，Agent 也不能为了让接口通过，随手把它命名为“手续费”。

银行另列的手续费，按实际材料记成手续费流水；如果材料不足，就继续查，或者把差异交给人。当前整批关联要求金额一致，并不是一个能自动处理所有手续费、退回和拆分情况的对账引擎。

银行流水里的金额也不能在关联时被改掉。关联可以纠正或清除，但不能把“我们的解释变了”写成“银行当时扣了另一个数”。

关联保存以后，这一行会从未关联列表里消失。我们没有另存一个“已对账”的开关；列表根据已有关系计算。可从列表里消失，只表示它已有记录来解释，不代表 Agent 的判断从此不需要核对。

这一轮真正改动的分工是：软件把银行事实、付款事实和两者的关系记清楚，守住方向与金额；Agent 去找材料、解释差异、组织确认，再推进记录。把一笔钱和十张单接起来，靠的是这两边各自做好自己的部分。
