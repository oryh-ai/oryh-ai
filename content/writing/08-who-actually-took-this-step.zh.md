# 这一步，到底是谁做的？

*《当 Agent 开始操作企业：ORYH 的设计探索》· 第八篇*

打开一张单的审批记录，看见“总经理已批准”，好像就可以继续了。但如果这条记录是 Agent 写的，我们还得问一句：它代表谁写的？

替员工整理材料的 Agent、替经理记录决定的 Agent、负责把流程往下推的 Agent，都可能调用同一套接口。调用成功，只能说明系统接受了一个动作，不能把这几种责任混在一起。

我们起初更担心 Agent 越权，后来却遇到了另一头的问题：它明明可以做，反而把自己拦住了。

## 换了一份工作，不等于换了一个人

有一次，同一个用户既是流程管理员，也是总经理。他先让 Agent 做了一些管理操作，后来又要求它记录自己的审批决定。

Agent 犹豫了。它把自己前面做过的管理工作，当成了“现在是管理员身份”的证据，觉得再记录总经理的决定可能是在冒充别人，于是拒绝继续。

这个担心听着挺谨慎，但前提错了。一个人可以承担几种职责，并不会因为刚才改过设置，就变成另一个人。

我们回头检查代码，发现个人绑定凭证的归属已经由服务器确定。写入审批记录时，服务器使用经过认证的用户，忽略请求里另外填写的审批人身份。Agent 不能靠换个名字，把这次操作记到同事头上。

缺的是把这件事告诉 Agent。后来我们补进操作说明：先查询当前凭证属于谁，不要从自己的工具调用历史猜身份。角色说明能做哪些事，用户身份说明这些操作记在谁名下。

这次没有新加一条后端限制。我们修的是 Agent 对已有边界的理解。

## 不能只靠一句“请不要冒充”

不过，也不能因此说所有凭证都一样安全。

ORYH 仍有允许调用方显式填写归属的服务凭证，用来兼容服务集成。这类凭证和绑定个人的凭证不同：调用里写了谁，可能就会记成谁。拿着它替某个人记录审批，不能把“接口允许”当成“这个人已经授权”。

所以操作说明也得把真正需要停下来的情况说清楚。用服务凭证准备写下个人决定时，应先停下来说明归属风险，确认合适的身份和授权方式。日常个人审批，我们更希望使用绑定本人的凭证。

负责推进流程的 Agent 也有自己的责任。它可以根据已有审批事实安排下一项工作，但不能因为流程需要一个“同意”，就替审批人补上这个决定。需要人批准的地方，仍然等人批准。

这里的软件要做两件确定的事：核验这份凭证有没有相应权限，把操作归属记准确。至于材料是否充分、该不该退回、接下来交给谁，仍然由 Agent 按公司规则判断和推进。

## 记住了谁，也还没回答完

身份记对了，并不代表决定就一定有依据。

服务器能确认请求用了谁的凭证，却不能仅凭这一点知道，这个人是否看过材料、是否真的表达了同意。Agent 如果把一句含糊的话理解成批准，记录里的名字可以完全正确，决定仍然可能错。

这也是我们不想把审计当成万能答案的原因。审批意见、相关材料和当时的业务记录要能够回看，Agent 则要在确认不足时继续问，而不是拿“我有权限”替代人的意思。

软件负责记录，Agent 负责逻辑，这条分工到了身份问题上，需要再多说半句：Agent 有权做什么，和人决定做什么，也得分开。

我们现在更愿意逐项核对：谁发起了操作，这份授权允许什么，留下的记录又表达了谁的决定。只写一句“Agent 已处理”，实在省略了太多东西。
