# 商品名字对不上，先别让 Agent 猜

*《当 Agent 开始操作企业：ORYH 的设计探索》· 第十篇*

做渠道订单导入时，我们被一列商品名称卡住了。

最初，ORYH 按平台商品 ID 保存对应关系：外面的这个商品，是我们商品库里的哪个。但商家下载的订单表里，可能只有商品标题和规格，根本没有 ID。映射表有了，拿到手的材料却查不了。

于是我们让映射也能按标题查询。原始标题照样保存，程序处理大小写、全角空格这些形式差异。接着又碰到一个问题：以前没见过的标题，该对应谁？

## 搜出来的第一名，还不能直接入单

拿我们测试里的例子来说，平台写着“【官方旗舰】保温杯500ml樱花粉 便携随行杯”，内部商品叫“保温杯 500ml”，旁边还有一款 350ml。

整段文字搜索很容易漏掉；删掉促销词再搜，也不保证就找对了。容量、颜色、包装数量，哪一个看错，后面的订单都可能跟着错。

我们在软件里增加了候选搜索：把中文拆成相邻的双字片段，结合英文和数字词项，按共有词项排序。这样，没有空格、词序换过的商品名，也有机会被找出来。

这里值得停一下。软件负责记录，不代表软件只能存取数据。搜索、计算、校验这些确定的工具，仍然应该由代码做好。但搜索分数只说明文字重合程度，不能直接当成“这就是同一件商品”的概率。

候选接口只返回列表，不替 Agent 选商品，也不写映射。

## 确认一次，要留下能再用的记录

我们把后续怎么做写进了 Agent 的 Skill：先查已有映射，没有才找候选；把同一批订单里尚未确认的标题收集起来，带上商品编码、名称和规格，一起问人。

问题也得问得具体：这条是 500ml 的樱花粉款，还是另一个规格？如果候选都不对，就保留这个空缺，不能为了导入完成硬选一个。

Agent 在这里负责理解材料、发现差异、组织确认和继续办理。有些判断需要补充业务事实，向人问清楚也是它推进工作的一部分。

确认以后，对应关系才写回 ORYH。来自哪个渠道、原始标题是什么、对应哪个商品、数量是多少，都成为可查询的记录。下一批再遇到同样的商品，就先读这份记录，不必从头猜，也不必依赖上一个 Agent 的聊天记忆。

我们还调整了权限。原来映射只能由商品管理员维护，每个新标题都要转一次手。现在有订单录入权限的人可以保存标题映射，创建商品仍需商品管理权限。把已有商品认出来，与往商品库里加一个商品，是两件不同的事。

## 推进过程留给 Agent，结果留在软件里

这一轮没有在后端加一条“相似度超过多少就自动选中”的业务规则。软件保存映射、检查权限和记录约束；Agent 依据已有记录决定是继续导入、补充查询，还是等人确认。

映射也有时间范围。上架链接没换，里面卖的东西可能换了。Agent 要拿订单发生的日期查询，软件返回那一天有效的对应关系，不能拿今天的商品解释昨天的订单。

测试里，我们检查了词序变化后候选还能出现、标题空格变化后已保存的映射仍能查到，以及录单人员不能借此新建商品。Skill 的检查则保留“先确认，再写映射”的顺序。这些能验证接口和说明的边界，还不能证明 Agent 在每次实际操作里都会照做。

遇到未确认的新标题，仍然要打扰人，这是当前选择的代价。我们想继续观察的是：问题有没有问清楚，确认有没有真正留下来，下一次是不是少问了一遍。软件负责记录，Agent 负责逻辑，这个分工就在这些小地方一点点落实。
