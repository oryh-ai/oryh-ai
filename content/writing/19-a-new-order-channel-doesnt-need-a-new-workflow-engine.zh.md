# 电商订单来了，改规则，还是改软件？

*《当 Agent 开始操作企业：ORYH 的设计探索》· 第十九篇*

上一回聊到，Oryh 的定制化可以从用户的一段话开始。这次想接着讲一个实际遇到的问题：新的一段话，和原来的规矩撞上了怎么办？

在一次电商订单场景测试里，管理员给 Agent 的要求很直接：平台订单不要求合同号，以平台单号为准，收货地址必须有；确认后先占货，不拣货直接发。

这些话描述的是企业怎么做事，不是一份等程序员翻译的功能清单。我们希望 Agent 读懂后，使用已有订单、占货和发货能力推进，软件保存规则与过程中发生的事实。

## 新规矩加上了，旧规矩还在

测试里，管理员还要求保留原来的规则，把电商这段加在后面。于是同一份流程定义里，同时出现了“来源报价号必填”和“以平台单号为准”。

原来的业务从报价成交开始，要求报价号很自然。平台订单却可能直接来自消费者下单，没有先做一张报价单。

这次 Agent 把电商条款理解成平台单号可以替代报价号，订单继续往下走了。但我们不能因此就说问题解决了：另一个 Agent 会不会按前面的通用条款，把同一张单退回？

如果这时给后端加一个“电商订单免报价号”的分支，眼前的问题很好处理。可下一家公司提出另一种例外，又要加一个分支。自然语言只是需求入口，真正决定做法的仍然是程序。

我们要保留的分工恰恰相反：Agent 管逻辑，软件管记录。企业规则的解释，不应该悄悄搬回后端。

## 要补的是 Agent 怎么读规则

后来我们补了推进订单的 Skill：定义里有明确针对这类订单的具体条款，就按这段条款处理，并在处理说明里交代采用了哪一句。不能只给一句“已确认”，把中间的判断藏起来。

如果定义根本没有授权用平台单号替代报价号，就不要自行发明这种等价关系。应退回并指出缺少渠道订单的规则，让有权的人补充。

这不是让“写在后面的话永远优先”，更不是看见“电商”两个字就跳过检查。Agent 得先确认订单属于哪种场景，再判断规则有没有明确覆盖它。真的说不清，就把矛盾讲给人听。

用户也不必为此学会流程引擎。可以继续用业务语言把范围说清楚，比如：“平台直接成交的订单不要求来源报价号，线下报价成交的订单仍然要关联报价。”这是一种可供确认的澄清，不该由 Agent 默默替企业补上。

软件保存新版本，也保留旧版本；Agent 读取适用规则，再结合订单事实决定下一步。改变的首先是企业自己的说明，而不是再造一套订单程序。

## 软件仍然有必须补的部分

这一轮并不只有文字调整。测试还发现，同一个平台单号可以被挂到另一张订单上，容易把重复导入记成两笔业务。

这类问题我们改在代码里：同一来源、同类单据的外部编号，已经关联另一张订单时要拒绝并指出原单；确实需要拆单，调用时明确声明拆分。Agent 判断是否应该拆，软件记录这个明确动作并检查关联。

“平台订单需不需要报价号”与“同一个平台单号已经挂在哪里”，是两类问题。前者是公司的做法，后者是记录之间可以核验的关系。

这也是自然语言定制真正有价值的地方：新增一种做法，不必自动变成新增一套程序。企业把规则说出来，Agent 负责理解、澄清和执行；软件把事实记清楚，把确定的约束守住。

当然，补一段 Skill 不等于所有 Agent 从此都会理解正确。这次把处理原则写清了，后续仍要拿不同订单、不同措辞去验证。我们要做的不是让自然语言听起来像魔法，而是让企业能用自己的话改变做法，并且看得见 Agent 为什么这样做。
