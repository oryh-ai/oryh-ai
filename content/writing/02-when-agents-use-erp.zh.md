# 如果用 ERP 的主要是 Agent，软件要怎么写？

*《当 Agent 开始操作企业：ORYH 的设计探索》· 第二篇*

工时服务做出来以后，一个问题慢慢变得具体起来：以前是人打开页面填单，现在换成 Agent 调 API，软件本身需要变多少？

乍一看，好像不用变太多。员工说“帮我报一下这周工时”，Agent 整理数据、调用接口，最后说一声“好了”。给原来的系统加一层聊天入口，似乎就够了。

后来做 ORYH，才发现不少原本不太显眼的地方，在 Agent 手里会变成问题。

## 有 API，其实还不够

一个挺典型的例子是改日期。我们曾经有个更新接口不接受日期字段，但请求里带了这个字段，服务器也不报错：忽略它，然后返回成功。

如果是我们自己写的前端，字段都是预先安排好的，这个问题不容易暴露。Agent 却可能根据用户的要求尝试修改日期。它收到成功响应，很容易告诉用户“改好了”，实际上什么也没变。

这就有点麻烦。用户看不到底下发生了什么，还得依赖 Agent 的转述。

后来我们把请求校验改严了：不支持的字段直接拒绝，并明确告诉调用方哪个字段有问题。这不能保证 Agent 一定知道怎么修，但至少不会让它拿着一个假的成功继续往下走。

原来藏在页面里的约定，不能指望 Agent 自己猜出来。接口得把能做什么、没做成什么说清楚。

## 少几次调用，不只是快一点

另一个问题是建单。最初接口按数据表拆得很自然：先建单头，再逐条建明细，最后提交。普通程序写个循环就行了，没什么特别。

但 Skill 也照这个顺序教，Agent 就一轮一轮地做。一张五天的工时单，要等好几次。接口本身并不慢，时间花在 Agent 不断读取结果、发起下一次调用上。

后来改成一次创建整张单据，明细跟着单头一起传。顺便也解决了一个一致性问题：某行不合法，整次创建回滚，不会留下半张单子。

不过，提交仍然是另一次操作。让人核对内容、明确确认的那一步，我们不想为了少一次调用也省掉。

回头看，接口的单位开始从“一张表的一次写入”，变成“这件事里一个完整、可确认的动作”。这比把按钮换成聊天框要多想一层。

## 那界面还要不要做？

当然要。管理员需要查权限，审批人可能想直接看明细，出问题时也得有地方翻记录。不能因为日常操作交给了 Agent，就让公司只能通过聊天知道自己的业务发生了什么。

只是，我们不再默认每项能力都得先做一张页面，再教员工怎么用。

比如“这张单接下来找谁”，我们更希望 Agent 读取公司的工作流定义来判断，而不是往后端继续加条件分支。ORYH 保存单据、规则文本、待办和审批事实。订单明细合计、权限检查、不能超额核销这些硬逻辑，仍然由代码守住。

所以这里的变化也不只是操作入口。原本放在应用里的业务判断，开始交给 Agent；留下来的软件，主要负责把记录存准确，把不允许发生的事情拦住。

现在遇到新需求，我们会多问一句：应该加一个页面、补一个接口，还是把公司规则写清楚，让 Agent 去做？

这几种选择，我们也不是每次都分得准。不过从“先想页面怎么画”变成“先想 Agent 需要知道什么、服务器必须保证什么”，确实让不少设计走向了不同的方向。
