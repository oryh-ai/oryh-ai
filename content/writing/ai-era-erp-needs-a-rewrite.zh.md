# AI 时代的 ERP，得重写，不是加个 Agent

*《当 Agent 开始操作企业：ORYH 的设计探索》· 随笔*

今天想把一个判断说得直白一点：AI 时代的 ERP，绝不是在原有 ERP 上加个 Agent，而是要彻底重写软件。

我们做 Oryh，想改变的就是这层分工：软件负责记录，Agent 负责逻辑。如果业务判断仍然牢牢写在原来的程序里，定制化的结就没有解开，只是多了一个能说话的入口。

## Agent 会操作，不代表企业能按自己的方式做事

比如一家公司习惯项目经理确认后，由财务付款；软件却要求中间必须再建一张单、走一轮审批。现在接上 Agent，它确实能替人点完这些步骤。

但如果企业说：“我们不需要中间这一步呢？”

只要后端仍把它当成必经步骤，Agent 就绕不过去。最后还是得改程序，或者让企业改做法。原来的实施难题还在，操作变方便了而已。

我们不想把“让企业适应软件”这件事自动化。也不想给每家公司配一个 AI 程序员，更快地生成一套定制代码。那样只是分支长得更快，后续维护的账还是要算。

## 我们自己也干过这种事

Oryh 的报销结算就走过一次弯路。

为了防止重复结算，我们曾要求所有报销先转成应付单据，再付款核销，关掉了直接对报销单核销的路径。技术上看起来整齐，却顺手替公司决定了管理方式。

有的公司需要应付单据，有的希望批准后直接结算。为什么必须选我们喜欢的那一种？

后来我们恢复了直接核销，把代码改成约束两条路径不能重复结算同一笔费用。公司采用哪条路径，写进规则，由 Agent 读取并推进；没写清楚，就问人。

这个改动很小，但区别很大：软件应该保证账不会因为两条路径被重复记，却不该因此要求所有公司采用同一种报销管理方式。

如果不改掉后端原来的限制，再聪明的 Agent 也只能执行那个限制。这就是我们说“得重写”的原因。

## 重写以后，实施在忙什么？

重写不是丢掉业务模型，也不是把所有计算交给模型。订单明细合计成订单金额，付款不能超额核销，权限不能越过，这些硬逻辑仍然由代码保证。

要拿出来的是公司怎么做事：谁先看，什么情况加审，缺材料怎么办，遇到例外找谁确认。软件保存事实、规则及其版本，Agent 结合这些记录作判断，把下一步推进下去。该由人批准的，仍然等人批准。

我们在演示里也试着用同一套内置订单记录，承载制造企业的发货签收和咨询团队的项目交付。两边的工作方式放在各自的流程定义和 Skill 里，没有为此各写一套订单后端。这只是一个具体范围内的验证，不是所有行业都已经解决了。

这样，实施才有机会从“怎么把企业塞进现成流程”，变成“把这家企业的做法说清楚，再拿实际案例验证 Agent 能不能照着做”。规则调整，也不必动不动就变成应用程序的开发和发版。

当然，定制化需求不会凭空消失。新业务事实装不下，记录模型就得补；规则有歧义，就得澄清；数据迁移、权限和验证也不会自动完成。我们想拆掉的是“管理方式一有不同，就要改一遍软件”的绑定。

企业当然可以主动改进管理，但不应该只因为软件里预设了一条路，就被迫大幅改变自己的做事方式。

所以，Oryh 要探索的不是给旧 ERP 配一个更聪明的操作员，而是重新写清楚软件到底负责什么。软件把记录做好，Agent 按企业的规则负责判断和推进。这才是我们认为 AI 时代值得重写一套 ERP 的理由。
