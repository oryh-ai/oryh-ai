# 给了通用对象，Agent 却绕开了已有的业务结构

*《当 Agent 开始操作企业：ORYH 的设计探索》· 第十一篇*

有一次导入历史数据，Agent 写进了约十五万条记录。客户、商品、报价单、销售订单，看起来都导进去了。

再看 Oryh 原本的客户库、商品库和业务单据，却还是空的。

数据没有丢。Agent 给这些数据各建了一种通用对象，名字就叫 customer、product、quote、sales_order，然后一路往里写。它没有停下来问人，软件也没有拦。

这件事让我们重新琢磨了一遍“软件负责记录，Agent 负责逻辑”：记录，到底要负责到什么程度？

## 有结构，不等于把业务逻辑写死

通用对象本来是留给那些没有现成结构的业务记录的。比如保修卡、设备交接单，公司可以定义自己的字段，不必等我们为每一种单据开发一个模块。具体怎样办理，仍由 Agent 读取规则来推进。

但商品已经有地方放了。

订单明细里的商品引用，指向的是商品库中的记录。通用对象里即使有同样的编码、名称和价格，也不会自动成为这个引用的目标。问“有哪些商品”，从两个地方查，会得到两套答案。

我们需要保留的，是一套大家都能使用的记录结构：哪张单引用哪个客户，哪条明细对应哪个商品，数量和金额怎样核对。至于给不给折扣、遇到例外找谁确认、接下来怎么办，留给 Agent 根据公司的规则判断。

把业务逻辑交出去，并不意味着连记录之间的关系也可以随手再造一套。

## 我们原来把一道确定的检查也交给了 Agent

原先的想法是：这家公司说的“产品”，究竟是不是系统里的商品，要由 Agent 理解，服务端不替它决定。所以即便通用对象直接叫 product，也能创建。

这次导入说明，我们把边界放得太宽了。对于已经明确公布的类型名称，软件完全可以守住。

后来，创建通用对象或类型定义时，只要名字是已有集合的名称、单数形式或列出的少量别名，服务端就拒绝，并告诉调用者应该写到哪里，有批量导入入口的也一起指出。

测试同时保留了另一面：product 会被拒绝，merchandise 这样的名称仍能通过。软件检查的是明确的名称冲突，没有假装自己理解了所有业务词汇。

于是，另一半工作仍然在 Agent 那边。

## 能创建，不等于已经想清楚

我们在相关 Skill 里补上了共同要求：提出自定义对象以前，先读系统已有类型的清单，比较业务含义。名字叫“货品档案”，也可能仍然是在说商品；只是多几列，就先考虑现有记录的扩展字段。

确实要新增一种类型，Agent 得在第一条数据写入前讲清楚：叫什么、准备放多少数据、来自哪里、已有结构为什么不合适，再等人明确确认。用户说“把表导进去”，不能被理解成“同意你另建一套客户库”。

如果已有相近的类型，却确有独立保留的理由，这个理由也要由人说明，写进类型定义。下一位 Agent 才知道它为什么存在，不用重新猜。换成 product_2 来绕过报错，不算理由；人的确认也不会取消服务端的重名限制。

这些限制是在拦住新的错误写入，并不是旧数据的自动修复。处理已经放错位置的记录，还涉及核对、迁移和重新建立关联，改个名字就算完成是不行的。

我们现在仍然保留通用对象，也仍然让 Agent 负责判断。只是“软件负责记录”有了更具体的含义：它要把记录的身份、关系和确定的约束守住。Agent 则要在这些事实上作决定，并把选择的理由也留成记录。否则，它今天很顺手的一次导入，就可能变成下一个 Agent 永远看不懂的另一套账。
