# Agent 会掉线，事情不能跟着丢

*《当 Agent 开始操作企业：ORYH 的设计探索》· 第六篇*

让几个 Agent 一起完成一条业务流程时，很容易先想到事件：单据提交了，发一个事件；主管批准了，再发一个事件；流程 Agent 订阅这些事件，然后继续往下做。

普通程序这么配合并不奇怪。放到 Agent 身上，我们却很快碰到两个问题：游标应该放在哪里，以及读到事件到底算不算处理完成。

一个 Agent 读到“主管已批准”，正准备安排财务复核时超时了。如果游标已经前移，这件事就丢了；如果游标没动，下次又会重复处理。再加确认、重试和死信队列，最后我们会重新造出一套消息系统，但仍然不知道 Agent 是否真的理解并完成了任务。

## 不追消息，改为检查还有什么没做

后来 ORYH 不再用事件流协调 Agent，而是让业务状态自己说明有没有工作等待处理。

待办就是人的收件箱：`open` 表示还在等，`completed` 表示已经处理。流程 Agent 查询的也不是“我上次读到第几个事件”，而是“有哪些已提交的单据目前没有开放待办”。只要一张单还没人接手，它每次查询都会重新出现。

这样一来，Agent 中途消失并不会抹掉进度。另一台机器、另一个 Agent，甚至同一个 Agent 重启以后，都可以重新读取单据、审批记录和待办，从当前事实继续。

审计日志仍然保留，但它只回答谁在什么时候做了什么，不再承担投递任务。通知也可以把 Agent 更快叫醒，可通知丢了最多晚一点处理；下一次检查仍然能发现那张单。

## 状态查询也会留下半件事

这套思路并没有自动解决所有问题。我们遇到过审批事实已经写入，但要求审批的待办没有关闭。记录一边说“已经批准”，另一边却还说“请处理这项审批”，这条流程就这样停在那里。

退回操作更明显：写一条退回记录、把单据改成 `returned`、给提交人新建修改待办，原来是三次调用。Agent 在任何两步之间退出，都会留下一套彼此矛盾但单看又都合法的记录。

后来我们把这些必须一起成立的事实放进同一个事务。审批决定会同时收掉对应待办；一次退回可以连同新状态和交接待办一起写入。要么全部成功，要么一项都不留下。

这不是把业务判断拿回服务器。由谁接手、退回到哪里、状态该变成什么，仍由 Agent 根据公司的规则决定。代码只保证：既然 Agent 已经作出这次决定，组成这个决定的几条记录不能只落下一半。

## 重试应该是一件普通的事

Agent 调用接口后，也可能没等到响应。它无法确定服务器没收到，还是服务器已经写完、只是在返回途中断了。

因此，审批记录和任务分配都需要能够安全重试。相同的业务事实再来一次，服务器返回已经存在的那一条，而不是再造一条审批、再派一个待办。对 Agent 来说，重试不应该是一场猜谜。

现在我们更愿意把 Agent 看成会随时离开的协作者，而不是常驻内存里的流程线程。对话、通知和运行上下文都可以消失，单据、审批事实和未完成工作必须留下。

这也自然带来了后面的问题：既然工作一直留在队列里，谁来定期看一眼，并把它继续往前推？
