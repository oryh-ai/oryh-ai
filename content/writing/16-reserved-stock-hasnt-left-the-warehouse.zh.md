# 货被占了，和货已经出库，是两件事

*《当 Agent 开始操作企业：ORYH 的设计探索》· 第十六篇*

销售答应给客户留三件货，仓库却还没有发。这个时候，库存到底该不该减？

只留一个数字就很别扭。减了，货明明还在货架上；不减，下一个人又可能把它答应给另一个客户。

Oryh 把这两件事分开记。测试里，库位原来有十件，为订单占三件以后，在手量仍是十，可用量变成七。占货流水写明是哪张订单占了货，但不伪装成一次出库。

## 发货时，别再扣一次可用量

真正发走这三件时，又有一个容易漏掉的地方：可用量已经减过了。

如果出库时再照常扣三件，最后就会变成在手七件、可用四件。那三件货只走了一次，可用量却被扣了两次。

我们把这层配合放进代码。发货过账时，服务器先计算这张订单在该库位还占着多少，把本次发货消耗的占用释放，再记实际出库。两条流水在同一事务里完成，结果是在手七件、可用七件。

这里的“释放”不是货退回仓库，只是原来的占用已经被实际发货消耗掉了。

为此还补了分两次发货的测试：先占三件，第一包发两件，第二包再发两件。第二次只能消耗剩下的一件占用，另一件从未占用的货里出。不能每次都拿最初的三件来释放，凭空多出可用量。

这种加减关系不应该让 Agent 每次临时拼出来。软件负责记录，也包括把记录之间确定的数量关系算对。

## 后来，我们收回了直接写流水的入口

使用中还出现过另一种绕路：订单操作员说了“出库”，Agent 就跳过订单和发货单，直接追加一条扣库存流水。

数字确实变了，但它是因为什么业务变的，没有通过应有的单据链留下来。光在 Skill 里提醒“操作前确认”，拦不住这个问题。

后来我们撤掉了通用的库存流水写入口。占货和释放走订单上的专门动作，销售发货通过发货单过账，由服务器生成对应流水。Agent 不再自己挑一个理由、填两个差额，把事情算作办完。

同时补上数量检查：当前可用不够，占货要报出缺口；订单在这个库位只剩一件占用，就不能释放两件。错误应该告诉 Agent 要找人讨论什么，而不是鼓励它改一个数字再试。

## 什么时候占货，仍然不是代码替公司决定

有的公司确认订单就占货，有的直接从货架发。取消订单后是否释放、客户只取消部分时释放多少，也要先弄清实际决定。Agent 读公司的规则、订单和交付安排，取得需要的确认，再调用相应动作。取消时释放占用，在手量不变；发货时已由服务器消耗的部分，Agent 不要再释放一遍。

这里还得承认一个没补完的洞。最近的本地数据库并发测试里，可用十件，两个请求同时各占七件，都通过了，最后可用量成了负四。单次请求有数量检查，不代表并发下已经安全。

这处问题仍待修复。该补的是代码在同一保护范围内检查和写入的能力，不能靠提醒 Agent“别同时操作”来守库存。

所以，“软件负责记录，Agent 负责逻辑”并不是把库存难题都推给模型。什么时候为谁留货、缺货后怎么协调，由 Agent 按企业规则推进；占了多少、还剩多少、发走多少，软件必须把这些事实及其数量关系守住。货还在不在，和还能不能答应给别人，终于可以分开回答，但两边的工程工作都不能省。
