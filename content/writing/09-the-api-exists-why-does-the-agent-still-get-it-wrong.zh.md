# 接口有了，Agent 为什么还是会用错？

*《当 Agent 开始操作企业：ORYH 的设计探索》· 第九篇*

我们有一次让 Agent 填一张报销单。三条明细都已经通过接口写进去了，Agent 转头却告诉用户：“第三条还没有保存，所以现在不能提交。”

接口没报错，数据库里也确实有三条。错的是 Agent 还在相信几轮对话以前的记忆。

这件事让我们意识到，为 Agent 做好 API，只完成了一半工作。接口可以把每次调用设计得很清楚，但 Agent 什么时候调用、先读什么、写完以后怎样确认，还需要另一层说明。

## API 只负责把动作做对

API 最擅长回答的是一些确定的问题：这个字段能不能改，这个人有没有权限，金额合计是否一致，这次重试会不会重复记账。

请求合法，就把事实写准确；请求不合法，就明确拒绝。它不应该猜调用者真正想做什么，也不应该因为 Agent 看起来很自信，就放松这些约束。

但一组正确的接口，并不会自动组成一件正确的工作。

填完报销明细以后，Agent 还要把整张单重新读出来，向用户展示实际保存的内容，再等待确认是否提交。我们当时的 Skill 只写了“复述完整报销单”，没有说这份完整内容必须从哪里来。Agent 很自然地复述了自己的记忆，于是把已经发生的写入说成没有发生。

后来我们在所有“先写记录，再根据结果作判断”的 Skill 里加了一条共同规则：判断以前重新读取；如果记忆和读取结果不一致，以记录为准。

这不是在 API 上增加一条业务逻辑。它是在教 Agent 怎样使用记录系统。

## Skill 不是一份接口目录

我们现在更愿意把 API、Skill 和公司规则看成三样东西。

API 提供动作并守住硬边界。Skill 告诉 Agent 怎样完成一类工作：从哪里找记录，几次调用怎样组合，什么时候需要回读，遇到不确定该问谁。公司规则则回答这家公司希望怎样办事，比如什么材料可以提交、什么金额需要加一道复核。

三者会相互引用，但不能互相代替。

把所有接口说明塞给 Agent，它可能知道有一个“提交”动作，却不知道提交前要让人核对。把公司的审批制度写进 Skill，又会让每次制度变化都变成软件发布。反过来，如果只给一段自然语言规则，没有接口的权限和金额约束，Agent 一次误解就可能留下不成立的记录。

我们也碰到过另一个方向的错误。有人只是问“我有哪些待办”，Agent 却照着处理任务的步骤，把每张单据、审批历史和附件都翻了一遍，最后交出一份调查报告。它没有答错，但做了很多没被要求的事，也增加了泄露无关信息和产生新误解的机会。

后来 Skill 会把“查询一个事实”和“办理一件业务”分开。问列表，就先返回列表；真要处理，再读取处理所需的材料。

## 操作说明也是产品的一部分

传统软件里，页面会限制操作顺序：按钮何时出现，确认框里写什么，提交后页面展示什么。Agent 没有这条固定路径，Skill 在某种程度上承担了这部分工作。

所以接口改变以后，只改服务端并不够。字段、动作顺序、回读方式或者权限发生变化，相关 Skill 也要一起检查。它们需要测试，需要跟着真实问题修正，也需要控制长度，免得最重要的边界埋在一大段说明中。

软件负责记录，Agent 负责逻辑，并不等于在两者之间留一片空白。Skill 就在这片空白里，告诉 Agent 怎样可靠地读写记录，又把每家公司的判断留给各自的规则。

现在我们遇到一次 Agent 误操作，会多问一个问题：是接口允许了不该成立的记录，还是 Agent 没被教会怎样完成这件事？两种问题看起来都像“Agent 用错了”，修法却完全不同。
