# 软件负责记录，Agent 负责逻辑

*《当 Agent 开始操作企业：ORYH 的设计探索》· 第三篇*

做 ORYH 时，我们越来越常用一句话检查自己的设计：软件负责记录，AI Agent 负责逻辑。

以前做 ERP，一个需求来了，很自然就会想：字段怎么加，流程怎么配，后端在哪个条件下进入哪个分支。公司的做事方式，被翻译成软件能执行的规则。后来即使接上 Agent，如果判断仍然全在系统里，Agent 也只是换了一种方式操作它。

我们想试的是再往前一步。除了金额合计、权限、数据一致性这些硬逻辑，把业务怎么判断、接下来怎么推进，基本都交给 Agent。ORYH 留下来做记录系统，保存业务事实，也保存公司写下的规则，但不负责解释这些规则。

这话说着简单，写代码时却经常绕回老路。

## 我们也替公司做过不该做的决定

报销付款就走过一次弯路。有的公司习惯先把批准的报销单转成应付单据，再付款核销；有的公司希望直接对报销单核销，不多建一张单。

我们曾经关掉第二条路，统一要求先转应付单据。这样看起来整齐，也避开了两条路重复结算的问题。

但问题是，公司为什么必须按我们选的方式办事？

真正需要代码拦住的，是同一笔费用被结算两次。比如一张 1,300 元的报销单，如果在报销单和应付单据上各核销一次，两张单各自都没超额，合起来却记了 2,600 元。

后来我们恢复了直接核销，改为让两条路径互斥。走哪条，由 Agent 读取公司的规则来推进；已经走了一条，就不能绕到另一条再记一次。

“我们公司怎么报销”和“同一笔钱不能重复结算”，原来是两个不同的问题。前一个不该被我们顺手写成后端的统一答案。

## 那软件里还剩什么逻辑？

当然有。订单明细合计是多少，服务器就应该准确算出来，不能让模型凭感觉报一个数。付款不能超额核销，没有权限就不能写，重试同一个记账请求不能又记一次。

这些是记录成立的前提，不是让 Agent 自由发挥的地方。

但一张单有没有必要退回补材料、差额要不要找人确认、下一步由谁审批，是另一类问题。公司规则可能变化，也可能有例外，需要 Agent 结合事实去理解和推进。需要人批准的地方，仍然等人批准。

所以我们说“Agent 负责逻辑”，不是让它包办所有计算，更不是让它替所有人拍板，而是把业务判断从应用程序里拿出来。

## 规则也得留下来

这又带来一个问题：逻辑交给 Agent，会不会变成它每次临场发挥？

不能这样。公司规则得写下来。ORYH 保存带版本的工作流定义，Agent 读规则，再结合单据、审批记录和待办决定下一步。没写清楚就问，缺少依据就停，不该自己编一个流程。

记录也不只是一张单据的最终状态。谁批准了什么、这次推进依据哪版规则，都要有地方回看。否则 Agent 说一句“处理好了”，我们也不知道它究竟处理了什么。

现在碰到新需求，我们会先问：这是在保证记录正确，还是在替公司决定怎么做生意？

我们还在练习区分这两件事。有时加一个后端判断确实很顺手，却也把本来能由公司调整的做法固定了下来。ORYH 想探索的，就是让软件把事实记牢，让 Agent 按公司的规则把事情往前推。
