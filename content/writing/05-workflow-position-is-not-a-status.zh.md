# 审批走到哪了，不一定是一个状态

*《当 Agent 开始操作企业：ORYH 的设计探索》· 第五篇*

做审批流程时，最顺手的设计通常是给每一步一个状态：待主管审批、待财务审批、待总经理审批。看一眼状态，就知道流程走到哪里了。

如果流程永远是一条直线，这样挺清楚。但公司里的流程很快就不会是直线了。财务可能看完以后要求主管重新确认，法务和财务可能并行，有人退回修改后又要从头看一遍。同一个节点会重复出现，几个节点也可能同时存在。

继续加状态当然也能表达，只是很快会出现“主管已批、财务待批、法务退回”这样的组合。状态不再描述单据本身，而是在努力压缩整段流程历史。

## 状态只说单据处于什么阶段

ORYH 现在把两件事分开了。

一张工时单提交后，在整个审批期间都可以保持 `submitted`。哪些节点已经通过，看审批记录；现在事情在谁手里，看还没有完成的待办；接下来可能去哪，看公司的工作流定义。

状态只回答比较粗的问题：这张单还在草稿、已经提交、被退回，还是流程已经结束。它不再充当工作流的游标。

这样做的一个直接好处是，服务端不需要知道“财务之后一定是总经理”。审批人只留下自己的决定，并完成自己的待办。流程 Agent 再读取现有事实，判断下一步交给谁，或者是否已经可以结束。

不过，少用状态并不会自动让流程变正确。

## 我们也读错过审批历史

有一张工时单被退回后，提交人修改了七行内容，再次提交。流程 Agent 读取全部审批记录时，看见第一位审批人在上一轮已经同意过，就直接把新版本交给了第二位审批人。

问题在于，那次同意针对的是修改前的内容。假如第二位审批人继续批准，这张单就会在第一位审批人没有看过新内容的情况下完成流程。

后来审批记录增加了更明确的轮次。退回后重新提交，会开始新的一轮；Agent 判断“哪些节点已经通过”时，只能看当前轮。序号也从头开始，不能沿用上一轮留下的位置。除非公司的规则明确说某个节点不必重审，否则新的内容就重新走完整条链。

这里没有增加“第二轮主管审批中”这样的新状态。我们只是把已经发生的事情记得更准确：这是哪一轮、这一轮里的第几个决定，以及这次决定发生在退回修改之前还是之后。

## 少一点状态，多一点事实

这种设计也给界面带来一点麻烦。一个 `submitted` 标签不再能解释全部进度。想知道流程走到哪里，必须同时展示审批记录和当前待办。

但这份麻烦是值得的。状态看起来简洁，却很容易把并行、重复和退回重新提交藏起来；事实记录稍微多一些，却可以让人和 Agent 从同一份历史重新判断。

代码仍然守住状态转换是否合法、同一节点的决定不能因为重试写两次。至于下一位是谁、是否需要重审、什么时候把单据改成最终状态，则由 Agent 根据公司的规则决定。

我们现在更愿意把状态看成单据生命周期的路标，而不是流程引擎的当前位置。审批走到哪了，不是某个字段给出的答案，而是从业务事实里读出来的答案。
