# 从一张工时单开始：ORYH 的原点

*《当 Agent 开始操作企业：ORYH 的设计探索》· 第一篇*

2026 年 3 月 11 日，这个项目的仓库里还只有一句很宽泛的目标：为 AI Agent 提供业务应用。当天加入的第一个真正业务能力，也不是宏大的 ERP 或 CRM，而是一套很小的工时记录服务。

它能保存员工、项目、工时单和工时明细，也能记录审批结果。边界写得很克制：这不是完整的人力资源系统，不负责寻找经理，不执行审批路线，也不计算工资。它只是让一个 Web 客户端、API 客户端或 AI Agent 把工时事实写下来。

现在回看，这种克制比当时显得更重要。

## Agent 带来的第一个问题不是自动化

员工不会用数据库字段描述一周的工作。他更可能说：

> 这周主要在 ERP Upgrade 上做 API 设计，周三处理了 Globex 的接口联调。

Agent 可以把这句话拆成日期、项目、任务和小时数，再写成结构化记录。最初看，这只是一次自然语言到表单字段的转换：过去由人填写页面，现在由 Agent 调用 API。

但很快出现了一个更难的问题：结构化结果是 Agent 的理解，不是用户的原话。如果 Agent 选错项目、拆错日期，或者把一句含糊描述解释得过于确定，系统只保存最终字段，就再也无法回答“这个数字最初是怎么来的”。

因此，两周后，工时单增加了 `source_report_text`，专门保存用户最初的自然语言报告。结构化明细仍然用于统计和审批，原文则保留理解发生之前的证据。两者不是重复数据：一个是系统可计算的业务事实，一个是人和 Agent 可以回看、质疑并重新解释的来源。

这成为 ORYH 后来反复使用的一条原则：**Agent 可以作出解释，但不能让解释覆盖证据。**

## 删除也不应该让事实消失

同一次改动还为工时单增加了软删除和恢复。原因同样朴素：人会说错，Agent 会做错，业务记录也会被误删。但“这张工时单曾经存在，后来被删除”本身也是事实。如果直接抹掉记录，系统失去的不只是数据，还有纠错和追责的可能。

这并不意味着所有草稿都要永久保存，而是提醒团队：面向 Agent 的系统必须为修正留下路径。Agent 的优势是可以快速行动；相应地，记录系统必须让错误可见、可恢复、可审计。

## 第一个边界已经出现

早期工时服务还有一个后来变得很关键的选择：审批表只记录审批事实，不自动推进工时单状态。服务端知道某个人在某个时间批准或退回了什么，但它不知道下一位审批人是谁，也不知道一次退回是否应该重新走完整流程。

当时这还不是一套完整的“Agent 原生 ERP”理论，只是一个实际边界：确定的事实写进记录，公司的流程判断留在外面。随后，通用业务对象、待办、工作流定义、Skill 和流程 Agent 都从这个边界生长出来。

ORYH 的起点因此不是“怎样让 AI 自动运行一家企业”，而是一个更基础的问题：**当 Agent 开始替人操作业务时，什么必须比 Agent 的一次回答活得更久？**

团队当时的第一个答案很小：一张工时单、它的明细、用户最初说过的话，以及每一次审批留下的事实。后来系统扩展到订单、库存、发票、付款和工资，这个答案并没有改变——Agent 可以更换，模型可以升级，流程可以重写；企业已经发生过的事情，必须留在一个不依赖任何一次对话的记录系统里。
