# AI 少写客户专用代码，现场的人反而得更懂业务

*《当 Agent 开始操作企业》· 研发随笔*

如果企业软件不再把每家公司怎样审批、怎样补单、怎样处理例外都写成客户专用程序，现场工程师是不是轻松了？我看恰好相反。少写分支，意味着不能再用“需求已经开发完”替代对业务的理解。

设想客户说：“急单先走，材料月底补。”传统项目很容易把这句话变成一个条件：勾选急单，跳过某道校验。AI 项目则可能把原话交给 Agent。两种做法如果都没问清“先走到哪一步”，都可能把一件本来该谨慎处理的事推进过头。

## 真正的工作从追问开始

急单是谁认定的？销售说客户催得急，算不算？生产停线要等零件，算不算？可以先占库存、先生成采购单，还是连付款也能先做？“月底补材料”是补报价、补审批记录，还是补正式合同？月底到了没有材料，谁负责停下下一步？

这些不是模型参数。它们是客户的管理安排。一个能交付的现场人员，要把不同部门说的“急”摆在一起，找出冲突，弄清正式授权，和当事人约定哪些动作可先做、哪些绝对不能做。不是把访谈录音喂给 Agent，就算完成实施。

如果客户自己也说不清，现场人员应当敢于说“先别让系统自动做这一步”。他可以从低风险动作试起：记录急单理由、提醒负责人补证、列出待办；对发货、付款、承诺交期等有后果的动作，先要求明确确认。能划出这种边界，比会写一段炫目的提示词重要。

## 软件记事实，Agent 判断下一步

在我看来，AI 时代的 ERP 值得重新分工。软件负责可靠的记录：订单是谁的、明细和金额是多少、货实际出了多少、谁在什么时候批准过。订单明细合计、余额不能重复扣、权限不许越界，这些硬逻辑写在代码里。

Agent 读客户自己写的规则，联系订单、审批历史、库存和当前人员安排，决定此刻该推进哪一步。规则是自然语言，不必每次都编译成客户专用分支。客户后来补一句“设备急单可以先占货，但付款仍等财务确认”，Agent 可以在下一次判断时读到这句话。软件照样保存规则版本和操作事实。

这不是一句“AI 会理解”就能完成的设计。规则放在哪里，Agent 怎样找到正确版本，查询是否漏了分页，读到互相矛盾的要求怎么办，越权请求会不会被后端拒绝，都需要认真做。现场人员还要验证几类真实情况：标准单据、缺材料的单据、规则刚变的单据、已经执行一半的单据。

这里很能看出 FDE 与“会配置 Agent 的驻场同事”之间的差别。后者也许能把一句话贴进系统；前者应能判断这句话是不是足够让系统去碰钱、货和客户承诺。他不代替客户决策，却能指出缺了哪个决策。

更难的是规则会变。客户第一周说“急单先占货”，第二周发现有些急单只是销售为了赶指标提前标的，于是补一句“只有生产停线或合同约定交期内的订单算”。现场人员不能只改一句提示词就收工。他得看已经按旧说法占出去的货、尚未发出的订单和下游待办：哪些保留，哪些复核，谁有权撤销。Agent 负责按新规则判断以后怎么办，过去发生的动作仍得留在账上。

## 少写代码，不等于不做工程

如果需要把老 ERP 的订单导进来，识别重复客户、保留历史审批，数据迁移仍是工程。如果要连仓库设备或银行，接口、身份认证、失败重试仍要有人设计。如果产品把库存占用和实际出库混在一起，现场不能靠一个聪明 Agent 补出正确的数量关系；那是产品记录层该修的。

同样，Agent 决定“急单先占货”之后，服务端要在事务里检查可用量、建立占用记录，避免两个并发请求同时拿走同一批货。一个人的业务判断再出色，也替代不了数据库约束和故障恢复。

所以我说 AI 时代可以少写客户专用代码，是对产品架构提出要求，不是给厂商免交工程作业的许可证。现场人员把某条规则写成自然语言，不代表底下缺失的权限、审计和记录能力也会被自然语言变出来。

## 现场的专家，价值不在把每件事亲自做掉

资深现场人员像一个能把不同问题分开的人。他知道“缺一种记录”应回产品，“缺一个外部接口”应找工程，“公司没说清谁批准”应找业务负责人，“Agent 判断有歧义”应加证据和人工确认。四件事在会议上常被统称为“系统还不能用”，解决路径却完全不同。

他还得懂得把问题留给正确的人。客户说了一个危险但确实想要的做法，他不能以“最佳实践”为由偷偷改掉；客户要求绕过明确的权限边界，他也不能以“客户说了算”为由照办。真正的超级个体不是能一个人取代所有岗位，而是能在复杂现场准确划分哪些决定归谁。

这种能力的检验方式也很朴素。上线前让他挑几张最难的旧单据，解释 Agent 会读哪些事实、引用哪版规则、做出什么动作、在哪里停。上线后拿实际执行记录对照，看他有没有预见到的漏项。能这样交付的人，比只会展示“AI 自动处理一百张单”的人稀少得多。

部署报告也不该只写“成功率”。把 Agent 提出的动作分成自动执行、人工确认、因证据不足而停下三类，分别看有没有误推和漏推。停下不一定是失败；在付款和发货前知道自己不知道，恰恰是系统有边界的表现。现场负责人要向客户解释这个边界，而不是为了演示数字好看，把所有停点都改成自动通过。

做 Oryh，我们坚持软件管记录、Agent 管逻辑。曾有库存测试把“占货”和“出库”混为一次扣减，结果货只走一遍，可用量却减了两遍；这类数量关系必须由代码修正。另一边，某家公司取消订单后何时释放占用，则要由 Agent 读它的实际规则。现场人员如果分不清这两种问题，就算一句客户专用代码都没写，也称不上真正的 FDE。
