# 连客户谁说了算都不知道，部署的是什么？

*《当 Agent 开始操作企业》· 研发随笔*

一家公司给了项目组织图：项目经理负责交付，采购经理管供应商，财务负责人审批预算。现场工程师照图把人员和角色接进系统，看上去井井有条。

第一次真实采购就卡住了。项目经理说设备急用；采购经理说老供应商报价偏高，但知道交期可靠；预算负责人担心这笔钱挤占下月计划；财务负责人问，究竟是谁确认“急用”可以先走。组织图上的线都没错，却没有替大家回答今天这件事该怎样决定。

这个例子是设想，但现场问题往往就是这种质地。一个自称 FDE 的人若只会把职位表录进软件，连客户内部谁提供事实、谁影响决策、谁能正式批准都分不清，所谓“部署企业 AI”很可能只是把混乱自动化。

## 影响力不是审批权

熟悉老供应商的人，可能一句话就能影响采购选择。他了解交期、质量和过去的麻烦，这些经验应该被听见。但他不一定有权签这张采购单。反过来，财务负责人有正式批准权，也未必知道某台设备停一天会让生产损失什么。

把两种角色都粗暴地写成“审批人”，系统会要么绕过授权，要么丢掉重要事实。Agent 应该能向懂供应商的人取证，再把有依据的建议交给有权决定的人；软件则应阻止未获授权的人执行批准。懂客户组织，恰恰不是学会绕开正式流程，而是知道哪些非正式知识必须进入判断、哪些正式边界不能越过。

项目组织图通常写了“谁负责”，很少写“谁一皱眉，事情就得停下来”。在有些公司，车间主任知道设备一旦停机要付出什么代价；在另一些公司，长期负责客户关系的人知道一句承诺会引发什么后果。他们可能没有审批按钮，却是事前必须咨询的人。现场人员若只做角色映射，根本看不到这层。

## 几周驻场，能看见多少？

销售演示和项目启动会里，客户通常会给出一套正式说法。真正的组织运行藏在异常里：负责人出差时找谁，两个部门意见冲突时谁召集，紧急情况先报备还是先办，做错事由谁去向客户解释。没有几次具体事件，谁也很难只靠访谈把这些关系问全。

所以“驻场两周，我们的 FDE 已经懂你们公司”听起来很自信，也很危险。他可能记住了会议里发言最多的人，却不知道不在会上的预算负责人能否叫停。他可能看见采购经理在群里说“可以”，就以为那是正式批准。把这种误会写入 Agent 的工具说明，后面每张单都会沿错路走。

真正有经验的现场人员不会宣称自己已经读透客户。他会建立一张可核对的责任表：每类动作谁有最终授权，谁提供事实，谁必须被告知，意见冲突时升级到谁。它不是一次性画完的“政治地图”；每碰到例外，就用真实单据回看，看规则是否说对了人。

这种工作可能还要得罪人。某位资深同事实际影响很大，却没有正式授权；现场人员必须礼貌地请他提供意见，同时让批准动作回到有权的人手里。另一位有签字权的人总说“找下面的人决定”，现场人员也不能只靠口头习惯把权力转走。能守住这种边界，才谈得上企业级交付。

更麻烦的是组织会变。项目经理离职、财务临时代理、采购团队拆分，旧的聊天习惯还会继续存在一段时间。一次部署不能把“老王一直负责”写成永久关系。人员角色、代理期限和制度版本需要有出处和有效时间；Agent 遇到旧称呼时，应核对当下的任命，而不是因为旧记录多就默认旧人仍有权。

## Agent 很会找人，也可能找错人

如果把所有聊天记录和组织图交给 Agent，让它推断“谁最适合处理”，它往往能找到一个合理的人。合理不等于有权。一个人常被提及，可能是因为他总在协助收集资料；一个人很少出现在群里，可能正因为他只在最后批准。

因此，找相关人和执行授权动作应分开。Agent 可以根据记录提议“先找老供应商负责人核实交期”，但创建审批待办时，要看现行制度和权限。两份材料矛盾时，它不能私自选一个更方便的。软件保存人员、角色、审批事实和权限；Agent 负责解释为什么此刻要咨询谁、推进给谁。

这里少不了现场人的长期判断。他需要发现一种很常见的句子：“平时都找老王。”平时找老王做什么？给意见、代看、代批，还是只是他能最快找到资料？若不把动词问出来，一条貌似准确的“老王负责”关系就会慢慢替代真实的责任划分。

## 现场部署的是系统，也是责任链

客户看部署结果，不应只看“审批已经跑通”。要挑争议单据回放：谁提出急单，谁验证理由，谁给供应商建议，谁批准预算，谁能在证据不够时暂停。每一步有记录、有出处，换了人仍能看懂。

一个真正能独立交付的人，会在系统上线前把这些责任边界与客户说清。说不清的地方先留人工确认，不把会议上谁声量大当作授权。这个判断不可能靠一份“组织架构导入模板”或一次培训批量制造出来。

他还得给组织留一条纠错路：若 Agent 把待办推给了不该审批的人，谁能撤回、谁通知下一位、原待办记录怎样保留？企业对“找错人”的容忍度，往往低于系统团队以为的程度。纠错机制若没想好，部署所谓“自动找负责人”只是在把一次关系误判变成一串新的责任争议。

做 Oryh 时，我们让审批记录只记“谁在何时批准或退回”，不由后端擅自决定下一位是谁。下一步由 Agent 读取客户当前的工作流定义和待办，依据真实授权推进。这个设计给公司保留自己的管理方式，也把现场问题照得更亮：如果连客户谁能确认、谁能拍板都没弄清，部署再漂亮，推进的仍可能是一条没人负责的流程。
