# 现场项目经理就叫现场项目经理，何必冒充 FDE？

*《当 Agent 开始操作企业》· 研发随笔*

我认识的好项目经理，能把一家客户内部几拨人拉到同一张桌前，让问题有人回答、计划有人负责、风险不要拖到上线前一天爆炸。这工作很难，也很有价值。所以当有人把这类现场负责人统统改叫 FDE，我反而觉得是在轻视项目经理。

他明明做的是一份值得尊重的工作，却被暗示只有戴上“AI 专家”的名牌才够高级。客户也因此看不清自己到底买到了什么。

## 两个人都能让项目上线，方式却不同

设想两位现场负责人。甲把需求收齐，安排访谈，跟踪接口进度，遇到部门意见冲突就召集会议，最终把上线窗口守住。乙也做这些事，但他还能独立判断某个审批设计会导致重复付款，识别 Agent 正在读过期制度，提出记录层该补的约束，并推动问题回产品修。

甲是优秀项目经理，乙可能是我们所说的 FDE。两人都对交付有贡献。区别不在“谁会不会写代码”，而在谁负责技术与业务交叉处的判断。把甲也叫 FDE，并没有让他突然具备乙的能力；把乙只当催进度的人，又浪费了他的价值。

有的项目需要很强的项目经理，但未必需要长期驻场的高阶技术专家。有的项目业务风险高、产品边界还在探索，就需要乙这样的现场负责人。客户应该按实际需求选择，而不是被一串岗位缩写带着走。

两种人的工作成果也不该混着评。甲让项目按期上线，解决了跨部门配合的难题；乙识别出一次危险的自动执行，避免未来重复出错。前者不是“能力低一档”，后者也不一定比甲更会管理进度。岗位划分越诚实，团队越容易让对的人处理对的问题。

## 角色混了，问题就会失去主人

客户说“急单可以先发货”，项目经理可以组织销售、仓库、财务确认范围，并把决定记录成行动项。这是他的本职。如果会议没有说清“谁能认定急单”，他会让有权的人继续讨论。

所谓 FDE 还应能指出更深一层的风险：库存占用和实际出库是否分开记，发货接口会不会重复调用，Agent 在没有正式授权时会不会把群聊里的“先走”当成批准。项目经理未必需要亲自给出这些技术答案，但团队里必须有人负责。

如果全员都叫 FDE，客户以为第一个到场的人会解决所有问题；厂商内部则以为“FDE 已经在现场”，后方研发可以等需求单。真正需要产品修改的缺口，就在角色交界处来回踢。名称越高级，责任可能越模糊。

现场开发也一样。工程师把外部银行接口调通、解决失败重试、修正字段映射，非常值得敬重。他可以和 FDE 一起交付，但不要因为岗位叫法流行，就把接口开发写成“企业 AI 战略部署”。客户买的是可用接口，不是英文名称。

## 给客户一份诚实的人员说明

项目计划可以把人写清楚：谁负责进度和跨部门协调，谁能决定产品技术方案，谁有行业经验审核业务规则，谁负责客户专用的集成开发，谁在上线后接异常。一个人可能兼几项，但兼任要说明能力和时间。没有哪个角色，别用“我们有 FDE”四个字把空缺盖住。

到了现场，也可以把每个悬而未决的问题标上主人，而不是只标一个“FDE 跟进”。例如“客户确认急单定义”归业务负责人，“库存并发校验”归产品工程，“下周跨部门会议”归项目经理。三项都重要，却不能靠同一张待办卡上的高级头衔解决。谁真正有决定权，必须出现在项目记录里。

验收也分开。项目经理的成绩是里程碑清楚、风险及时暴露、交接不掉链；开发工程师的成绩是接口稳定、数据正确、故障可恢复；若真有 FDE，他还要证明 Agent 的业务判断有出处、硬边界被守住、关键异常有人能接。他们不必争一个更贵的名称，各自把工作做好就足够体面。

这也有助于客户采购。预算有限时，客户可以选择成熟产品加一位可靠项目经理，再按需请资深专家审高风险环节；不必为一个长期驻场“全能 FDE”买单。若项目确实复杂，客户也知道贵在哪里、谁为哪些判断负责。

供应商内部也因此少些错配。把擅长协调的人硬包装成“能独立做架构与业务判断”的 FDE，他一旦遇到技术争议只能假装确定，或不断向后方求救；把擅长深度技术的人长期派去催会议，也会消耗他的能力。诚实命名不是讲究礼貌，是降低交付风险和人才浪费。

## 为什么我对这个称呼这么不耐烦

因为 AI 的出现，本来应该让我们更清楚地区分“软件已经能做什么”和“现场还需要谁决定什么”。软件若只负责记录，Agent 负责逻辑，现场人员要帮客户核实规则、证据、权限和产品边界。有人承担协调，有人承担开发，有人承担复杂判断。这套分工可以非常好地交付。

可一旦所有人都叫 FDE，事情又变成了靠一个人包办。出了错，就说 FDE 培训不够；项目太贵，就说客户不愿为专家付费；上线后要改代码，就说“前线部署本来就包含开发”。一个漂亮称呼，替厂商省掉了说明产品边界和人员配置的麻烦。

我不反对真的有 FDE 的团队用这个称谓。我反对把现场项目经理换个名就卖成 AI 专家，也反对让认真做项目管理的人觉得自己原来的职业不够体面。许多项目靠好项目经理和好软件就能完成；需要高阶现场判断的地方，再明明白白请这样的人。

做 Oryh 时，我们希望软件留下单据、审批和操作的可靠记录，Agent 按公司规则推进。项目经理可以组织客户把规则说清、让上线有人负责；开发工程师可以把接口和硬约束做好；真正的 FDE 则应能在两者之间识别高风险判断，并把反复出现的问题带回产品。三种价值都实在，不必互相冒充。
