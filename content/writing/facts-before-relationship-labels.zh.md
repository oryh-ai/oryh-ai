# 别再神化本体论：关系图不是生意的真相

*《当 Agent 开始操作企业：ORYH 的设计探索》· 随笔*

前两篇聊本体，主要聊了两件事：把业务装进模型时，容易丢掉什么；模型建好以后，又怎么慢慢跟不上业务。

这次想说一个更直接的问题：关系本身，可能就是误判的起点。

企业 AI 很容易给人一种错觉：客户、供应商、产品都连起来了，它就懂业务了。但一张关系图画得再完整，也不代表它知道现在该怎么办。

## 供应商关系还在，生意可能早就不做了

举个例子。

“A 是 B 的供应商。”

这句话看起来很清楚。两个对象，一条供应关系。假如 Agent 正在替 B 找采购渠道，A 很自然就会进入候选名单。

再补一句：“A 最近一次给 B 供货，是五年前。”

感觉马上不一样了。

这五年，A 有没有换产品线？当年的联系人还在不在？现在的价格、产能和交期怎么样？都不知道。一个本来像是“找熟悉的供应商下单”的任务，变成了“联系一家历史供应商，重新确认条件”。

注意，五年没供货，不等于 A 不合适。它可能仍然是最好的选择。但“可以直接采购”和“值得重新了解”，是两种完全不同的判断。

决定这种区别的，不是供应商关系，而是发生过什么、什么时候发生，以及还有什么没确认。

对这次商业决策，最后一次供货的事实，显然比那个关系标签重要得多。

## 最危险的，不一定是假关系

问题甚至不需要关系建错。

A 确实给 B 供过货，所以关系成立。但 Agent 可能顺手做了几次推演：供过货，所以是熟悉的合作伙伴；是合作伙伴，所以已经通过审核；通过审核，所以现在可以继续采购。

每一步听起来都挺合理，连起来却可能完全不对。

一次试单，被理解成稳定合作；一个产品上的供货经历，被理解成对整条产品线的熟悉；五年前的资格，被理解成今天仍然有效。

关系标签把这些差别藏起来了。

关系再往外连，问题还会放大。A 给 B 供货，B 又是我们的重要客户，是否就能推断 A 对我们很关键？还得看供的是什么、占多少、能不能替代，以及业务现在是否还在发生。

多连几条线，并不会自动补上这些事实。我们担心的，正是把“关系已经建好”，误当成“决策证据已经充分”。

## 事实也不是一句没有出处的话

这里还得给自己加一道约束。

“最近一次供货是五年前”，也不能让 Agent 张口就来。

它查的是哪套记录？有没有完整迁移历史数据？其他部门是否还在向 A 采购？查到的是最后一次下单，还是最后一次实际收货？这些不是同一回事。

如果只查过当前系统，严谨一点的说法应该是：“在目前可见的收货记录里，最近一笔是五年前；是否有其他交易，还需要核实。”

没查到，不等于没发生。记录今天被修改过，也不代表交易今天才发生。

所以我们说软件管记录，不是往数据库里塞几句话就算完成。时间、数量、对应单据、来源，以及后来怎么更正，都影响 Agent 能不能用好这份记录。数据库里有一行，也不意味着现实已经被完整、准确地描述了。

我们要的事实基础，是能追问、能核对、能修正的记录，不是换个名字的确定口吻。

## 本体当然也能存事实，但这没有回答核心问题

有人可能会说，那就在关系上加时间、加交易明细、加来源。

当然可以。本体并不是技术上不能表达这些东西。[W3C 的 PROV-O](https://www.w3.org/TR/prov-o/) 就能表达来源和时间等信息。

我们反对的不是这种表达能力，而是把对象关系抬成企业 AI 的决策地基。

如果每次真正做判断，仍然要回到具体交易、原始材料和当前条件，那就应该把这些事实放在中心。关系是帮助查找和组织证据的工具，不是证据的替代品。

“这张订单属于哪个客户”当然也可以是一条明确的事实。我们并不反对关联，更不是要把数据库里的关联都删掉。我们反对的是，从一个宽泛的业务关系，直接跳到一个具体的经营决定。

## Oryh 要把这条界线守住

做 Oryh 时，这个问题会落到很具体的地方。

系统有供应商和产品的关联，也能记录最近价格；采购订单和收货记录又是另外的记录。但“这个供应商供过这个产品”“上次是这个价格”“这次已经收到货”，不能被压成一句“这家供应商没问题”。

下过单不是收过货，收过货也不自动意味着下一次交期可靠。软件把这些记录关联起来，是为了让 Agent 查清楚，不是替 Agent 把结论先写好。

接下来才是企业自己的逻辑。

比如用户说：“超过两年没采购过的供应商，重新询价；急单要由采购负责人确认。”

这是一段自然语言要求，不应该为了它去开发一套新的供应商判断模块。Agent 根据这段要求，查实际采购和收货记录，识别缺失信息，再决定询价、请求确认，还是继续推进。

另一家企业可能认可五年前的合作经历，但要求每次核实产能。那就按另一套要求判断，不必让两家公司先接受同一种管理模式。

当然，用户说完一句话，不代表所有条件都已经清楚。究竟按下单时间还是收货时间算“没采购过”？有歧义就问，有信息缺口就补，不能靠 Agent 自己脑补。

软件负责把事实记准，把金额合计、权限、重复写入这些底线守住；Agent 负责结合事实和企业要求，判断下一步。这才是我们想要的分工。

沿着这个方向，Agent 给采购人员的答复，也不该只是“推荐 A，因为它是现有供应商”。更有用的答复是：找到了哪些历史收货记录，最近一笔距今多久，哪些条件还没核实，按公司的要求为什么要重新询价。

这也是我们继续做产品时要检查的地方：Agent 给的是一个标签，还是一条能回去核对的判断路径？如果后来判断错了，人能分清是记录不完整、要求没说清，还是 Agent 推理出了问题。否则关系图再漂亮，出错以后也只剩一句“AI 判断的”。

## 先问发生了什么

本体最有诱惑力的地方，是让人觉得：把企业的对象和关系定义完整，就抓住了企业的运行方式。

但经营不是在一张关系图上走路。它面对的是不断发生、不断变化，还经常不完整的现实。

我们更希望 Agent 在做决定之前，先问：发生过什么？什么时候？依据在哪里？现在还有哪些不知道？

“A 是 B 的供应商”，可以是查下去的起点。

但绝不应该成为不再查下去的理由。
