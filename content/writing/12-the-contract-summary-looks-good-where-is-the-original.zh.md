# 合同摘要写得很好，原文在哪里？

*《当 Agent 开始操作企业：ORYH 的设计探索》· 第十二篇*

做合同模块时，我们在测试里放了一段付款条款：签订后三个工作日内付 30%，首批货物发出前付 60%，验收合格后付余下的 10%。

旁边的摘要是：“首付 30%，发货前 60%，验收后 10%。”读起来很顺。

可要是接着问，首付款有几天时间？是每批发货前都付，还是首批？只看摘要，就少了几处影响下一步判断的条件。

我们拿这个测试例子来梳理合同记录的边界：Agent 可以帮人理解合同，但软件不能只留下它理解后的版本。

## 原件、摘录和解释，分开放

我们把这几层东西分开了。

PDF、扫描页、Word 文件作为附件关联到合同。Agent 用自己的工具读取文字，需要识别图片就做 OCR，提取出的文字也保存下来，方便以后检索。Oryh 本身不做 OCR，更不替 Agent 解释合同。

接着，Agent 把付款、交期、验收等条款逐字摘出，记下来自哪个文件、哪一页、第几条。解释另放在摘要里。原文说了什么，Agent 怎样理解，两份内容可以一起读。

这样做也解决了另一个实际麻烦：每次有人问“付款怎么安排”，都重新读几十页文件，既慢，又可能漏掉不同的地方。现在可以先查付款条款，需要核对时再回到原件。

这里的分工很直接：软件负责记录，Agent 负责逻辑。软件保存材料和位置，Agent 负责提取、理解，并判断现有材料够不够回答问题。

## 有一句付款条件，还不等于现在就该付

“验收后付尾款”是合同里的约定。现在是否已经验收合格，则要去看业务记录。公司还要求谁确认，也得读公司的规则。

这些事由 Agent 结合材料来判断和推进。它可以发现还缺验收记录，向人问清楚，或整理下一步需要确认的事项。软件不会因为录入了“验收后 10%”，就在后端生成一条自动付款逻辑。

我们也把操作要求写进合同和付款相关的 Skill：回答或办理前读取相应条款，不凭聊天记忆；原文逐字保存，自己的解释另写。

如果条款列表没查到，不能拿一个“通常如此”的条件补上去。它可能没被提取出来，也可能合同确实没写。需要继续查找时，就搜索提取文字，再回到原文件。还不能确定的地方，应该把不确定说出来。

## 修正理解，和改变约定，是两回事

摘要漏了“三个工作日”，可以修正摘要。双方另签了一份补充协议，就不能用新内容盖掉旧合同。

我们给补充协议、续约留的是新合同记录，再关联原合同，各自保存文件和条款。下一位 Agent 才能看见先前的约定和后来的变化。

当前代码会按合同状态限制金额等约定字段和明细的修改，签署后这些内容被冻结；摘要、备注和条款摘录并不是全部锁死的。因此，不能笼统地说“签过字，系统里的每一段文字都不可变”。维护摘录与修改约定的区别，仍需要 Agent 遵守。

同样，代码能检查条款关联的文件是否属于这份合同，却不能证明 Agent 抄得准确、页码指得正确、摘要没有漏条件。我们的测试验证了原文件可以取回，条款查询能同时返回原文、摘要和页码。至于内容有没有读对，仍然要靠回查和必要的人工核对。

所以，这一轮我们在意的并不是摘要能写得多漂亮，而是有人问“你为什么这样判断”时，Agent 能不能把人带回那份材料。软件把依据留下来，Agent 的判断才有机会被检查、修正，再接着往下做。
