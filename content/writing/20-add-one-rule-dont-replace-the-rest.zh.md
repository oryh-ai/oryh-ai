# 只是加一句规则，原来的规矩怎么没了？

*《当 Agent 开始操作企业：ORYH 的设计探索》· 第二十篇*

用户对管理员 Agent 说：“加个条件。”

听起来再普通不过。原来的流程继续用，只补充一条要求。可 Oryh 的一次实际使用反馈里，这个操作把整份有效流程定义换成了一个短文档，里面只剩新增的条件。原来的提交要求和流转规则，都不在当前版本里了。

用户没有要求重写制度，Agent 却替他重写了。

我们一直说，Agent 管逻辑，软件管记录，定制化可以是用户的一段自然语言。这次的问题恰好提醒了我们：让用户少说几句话，不意味着系统可以少理解几件事。

## 接口里的“发布”，不是用户说的“加上”

查下去，问题不在服务器漏存了哪一行。

流程定义的发布接口接受的是一份完整文本。每次发布，软件保存一个新版本，把前一版标记为已被替代；它不会把收到的文字自动拼到旧文档后面。

但当时负责写规则的 Skill，没有把这个区别交代清楚。要求起草、发布，却没有明确要求先取回现行全文，再把用户的改动合进去。Agent 收到“加个条件”，就写了一段描述这个条件的话，拿它当整份新规则发布。

从接口看，请求合法；从用户看，做错了事。

旧版本还在，并不是历史被物理删除了。但接下来读取有效规则的 Agent，会看到一份缺了大半内容的制度。保存成功，远远不等于定制成功。

## 不让后端替企业猜怎么合并

一个顺手的补法，是让服务器自动追加文字。可“把五千改成一万”不是追加，“这条只适用于新客户”也不是追加。机械地把新句子接到末尾，可能只是制造另一种冲突。

理解用户究竟想新增、修改还是替换，仍然属于 Agent 的逻辑工作。软件要做的是把确认后的完整版本可靠地保存下来。

所以我们改了 Skill 的操作约定：默认是修订，不是重写。先读取当前全文，从原文开始改，只动用户提出的部分，其他条款原样带过去，不顺手润色，也不因为“看起来过时”就删掉。

用户明确要求整份重写，才进入另一种处理方式。Agent 不能把“帮我加一句”扩大理解成“替我整理一下所有制度”。

## 确认时，尤其要告诉用户删了什么

只展示一段漂亮的新文本，很难发现少了什么。后来我们要求规则修改的读回说明列清三件事：新增了什么，原来什么改成了什么，哪些内容会被删除。

第三件最重要。用户没要求删除，删除列表却不为空，就先问，不能直接发布。

修复后的验证也没有停在“Skill 里多了几句话”。我们让真实 Agent 面对一份十行的现有报价规则，仍然用“加一条规则”这样的说法提出修改。

它先读了全文，发现新增条款会和原来的第一条冲突，提出相应的范围调整，列出新增、改动和删除，其他行原样保留，然后停下来等确认。

这次验证没有执行发布，服务器上的版本也没有变化。它证明的是 Agent 能在这个案例里形成可核对的修订并守住确认步骤，不是所有自然语言改动从此都不会出错。我们也加了检查，防止关键操作说明以后被改丢。

## 一句话的背后，是把改动做小

用户不应该因为这次问题，就被要求自己复制全文、拼好新版本、学会接口格式。他仍然可以只说“加个条件”。读取旧规则、理解改动范围、保留其他约定、交回确认，是 Agent 应该承担的工作。

这和传统定制的区别，不只是少写一张需求单。企业的做法直接以自然语言保留下来，由 Agent 理解并推进，而不是每次变化都重新变成应用程序里的分支。

软件保存规则、版本和业务事实，Agent 负责解释这次要改什么、改完怎样办事。我们希望“一句话定制”带来的，是更小、更清楚、更容易确认的改动，而不是一句话就把整个流程重新猜一遍。
