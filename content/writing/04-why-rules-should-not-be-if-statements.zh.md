# 公司的规则，为什么不该是一堆 `if`

*《当 Agent 开始操作企业：ORYH 的设计探索》· 第四篇*

把业务逻辑交给 Agent 以后，马上会碰到下一个问题：公司的规则放在哪里？

最轻松的答案是，让 Agent 记住。比如告诉它：“一万元以内主管批，超过一万元再找总经理。”如果只有一个 Agent，规则也很少，这样确实能跑。

可是一旦填单、审批和推进流程的是不同 Agent，事情就没那么简单了。有人记着昨天的规则，有人拿到了刚修改的版本，还有人根本不知道规则改过。最后大家都说自己按要求办了，却很难回答按的是哪一版要求。

既然不能只靠记忆，工程师很自然会走向另一个答案：把规则写进代码。

## 一个条件很快会长成一套系统

“超过一万元加总经理审批”，写成一个 `if` 并不难。接下来可能还有：采购设备才加批，续费不用；某些项目先看预算；缺报价单先退回；紧急采购可以走另一条路。

于是一个条件变成一组条件，一组条件又需要配置页面、操作符和优先级。每次公司调整做法，都得确认代码有没有覆盖新的例外。

这当然可以做，而且传统工作流系统已经做了很多年。但如果 ORYH 也沿着这条路走，Agent 最后还是只负责触发一台规则机器。公司的流程逻辑并没有真正离开软件。

我们后来采用的办法，是把工作流定义作为一份自然语言记录保存下来。它可以写提交时要带什么，也可以写谁先看、什么情况下加批，以及退回以后怎么继续。Agent 每次推进前读取它，再结合单据和已经发生的审批作判断。

修改规则不是覆盖原文，而是发布一个新版本。旧版本还在，Agent 安排下一项工作时也留下自己参考的版本。这样至少能回答一个很朴素的问题：当时为什么把这张单交给了这个人？

## 自然语言不是随意发挥

把规则写成文字，并不意味着 Agent 想怎么理解都行。

“超过一万元由总经理加批”比较明确；“金额较大时最好让领导看一下，紧急情况可以从简”就有很多没说清的地方。多大算大，谁是领导，什么算紧急，都不该由 Agent 默默补齐。

我们的约束是：没有规则，就不要发明流程；规则有冲突或缺少关键条件，就停下来问，把问题留给制定规则的人。Agent 可以理解文字，但不能借“理解”替公司创造制度。

代码仍然负责另一侧的边界。没有权限的人不能审批，非法状态不能跳转，同一审批事实不能因为重试被记两次。这些约束不随着公司措辞变化，也不需要 Agent 判断。

## 难题只是换了地方

以前改流程，我们会讨论条件表达式有没有写对。现在更多是在讨论一句规则是否足够清楚，填单 Agent、流程 Agent 和审批人能不能得到相同的理解。

这并没有让流程设计自动变简单。自然语言也会含糊，规则之间也会打架，执行到一半时还可能发布新版本。只是这些问题终于出现在它们本来应该出现的地方：公司的规则文本里，而不是散落在后端分支中。

对 ORYH 来说，规则也是需要长期保存的业务资料。软件把它和版本记下来，Agent 负责阅读和执行，人则随时可以追问、修正，再发布一版更清楚的说法。
