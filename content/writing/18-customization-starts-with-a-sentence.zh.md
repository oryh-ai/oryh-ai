# 定制化，为什么不能就是用户的一段话？

*《当 Agent 开始操作企业：ORYH 的设计探索》· 第十八篇*

比如管理员说：“以后报销审批通过，直接对报销单核销，不再先转应付单据。”

我们希望这句话就是定制化的入口。用户说清自己的做法，Agent 理解、确认、保存，之后按这个做法推进。不是先写需求书，再等人把它翻译成另一套程序。

这不是因为 AI 写代码更快，而是因为职责换了：Agent 管逻辑，软件管记录。公司怎样办事不再全部塞在后端，改变做法，也就不必总是改软件。

但做 Oryh 时我们发现，从“支持自然语言”到这句话真正起作用，中间还有不少事要做。

## 能保存一句话，不等于 Agent 知道该怎么用

报销直接核销和先转应付单据，两条路径我们都已经支持。防止同一笔费用通过两条路径重复结算，仍由代码负责。

可管理员要切换做法时，说明却没接好。负责修改规则的 Agent，没有被明确告知这类要求应放在哪里；负责付款的 Agent，虽然被要求读公司规则，却没有清楚的查找顺序，连该找哪种单据的流程定义都曾指错。

于是，一句完全合理的话，落到哪个位置，还要靠 Agent 猜。

后来我们在两边的 Skill 里把这件事写具体：这种已有能力的使用偏好，保存为付款 Skill 的公司补充说明；付款 Agent 先读自己拿到的这段说明，再查报销单的流程定义。两边冲突，就指出来问人，不能自己选一个。

软件保存这句话，Agent 解释这句话。我们没有为“这家公司想直接核销”再写一条后端专用分支。

## 别为一句话，复制一整套软件

还有一个很容易走进去的岔路：把原来的 Skill 复制一份，改成客户专用版。

这看上去也完成了定制，但公司只是改了一个偏好，整份操作说明却从此和产品版本分开。以后通用 Skill 修了问题，客户那份不一定跟着更新。熟悉的定制版本维护负担，又换了一种形式回来。

所以我们把公司补充说明单独保存，不改原来的通用 Skill 文件。生成给 Agent 的说明包时，再把它附进去。产品能力继续更新，企业自己的做法也保留下来。

测试里，我们先写入直接核销，再改成先转应付单据，检查新版说明里出现新句子、旧句子不再残留，版本号也随之变化，同时确认它没有变成一份独立定制 Skill。

版本变化让已安装的副本能在后续同步时发现更新，不是所有在线 Agent 瞬间换了记忆。这项测试验证的是规则能被正确保存和送达，实际执行仍要拿业务案例检查。

## 用户不该先学会我们把规则放在哪

对用户来说，“超过某个金额加一级审批”和“报销直接核销”，都只是描述自己的做法。

前者应落进流程定义，后者可以是已有 Skill 的补充说明。识别区别、找到已有记录、解释准备改什么，是 Agent 的工作。用户不该先学会字段名和接口，才能定制自己的流程。

有歧义就追问：适用于哪个部门，从什么时候开始，原来的在途单据怎么办？这仍然是一段围绕业务的对话，不应该每次都变成开发项目。

这里的优势很实在：对已有业务能力内的规则调整，企业可以用自己的语言改变做法，而不必为每次不同都维护一份程序，也不必迁就软件预设的管理方式。

当然，一句话不能凭空造出尚不存在的外部接口，也不能绕过权限、金额合计和防重复结算这些硬约束。需要新工具、新记录结构的地方，仍有工程工作。

我们想做的，是把这部分工程留在产品能力上，把企业如何使用能力的选择交回企业。用户说规则，软件把规则和事实记住，Agent 按规则判断并推进。自然语言在这里不是需求说明的草稿，而是定制化本身的一部分。
