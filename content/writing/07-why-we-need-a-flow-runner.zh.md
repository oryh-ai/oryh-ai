# 为什么还需要一个 Flow Runner

*《当 Agent 开始操作企业：ORYH 的设计探索》· 第七篇*

经理点完批准，关上电脑。员工的 Agent 也已经结束对话。单据、审批记录和待办都在，可接下来该交给财务，这一步谁来做？

上一篇解决的是 Agent 中断以后，工作不会跟着消失。但工作留在系统里，并不意味着它会自己继续。

这就是 Flow Runner 要接的活：作为负责推进流程的 Agent，定期看看还有什么工作，读取公司的规则和当前记录，判断下一步该交给谁，或者流程是否已经完成。需要人审批就等人审批，规则没写清楚就停下来问。

## 谁来跑，可以自己选

最初的安排是客户自己运行流程 Agent。这个边界我们仍然保留：只要能读取规则、使用 ORYH 的接口，并拿到相应授权，客户就可以指定自己选择的 Agent 来推进工作流，也可以在自己的服务器上专门运行一个常驻的 Flow Runner。

不过，使用业务系统还得自己照看一个推进 Agent，这件事对一些客户来说有点绕。于是 oryh.ai 提供了服务端运行的方式，当前选择 Pi Agent 来做这份工作。

Pi 是 oryh.ai 的运行选型，不是 ORYH 对客户 Agent 的要求。它拿到任务和操作说明，调用公开 API，读取和写入同一套业务记录。换一种运行方式，不该要求公司把流程规则重新写成另一套东西。

但换人接手需要交接。如果客户自己的 Agent 和服务端的 Agent 同时负责同一批工作，双方可能各派一项不同的待办。接口看起来都合法，业务上却乱了。选择谁来推进，也包括说清楚各自负责什么。

## 常驻的程序，不负责解释业务

做服务端运行时，我们又碰到一个容易混淆的地方：既然有了常驻程序，是不是又写回了一台工作流引擎？

我们把这层拆开了。调度程序负责检查有没有待处理工作、何时启动、一次最多处理多少，以及连续出错后何时停止。队列为空，就不必叫模型起来看一遍。

真正决定“这一轮审批已经齐了”“还需要财务复核”的，仍然是 Agent。软件保存规则、单据和审批事实，也检查权限、状态合法性这些硬约束，但不在调度代码里写谁应该接在谁后面。

在目前的 Pi 接法里，常驻的是调度程序，每次运行都会启动新的 Agent 会话。进度从 ORYH 读取，不依赖一段永远不能断的聊天。接入运行时的代码也单独隔开，方便以后替换和比较。

## 正常退出，不代表事情办成了

我们真遇到过一个挺容易漏掉的问题：模型调用因为凭证失效而失败，Pi 进程却正常退出了。如果只看退出码，这次运行就会被记成成功，只是“恰好没推进任何事”。

后来我们补上了对运行事件中错误信息的检查，也把 Agent 自己报告的结果和运行前后的队列变化分开记录。它说自己处理了几项，是一种说法；系统里实际发生了什么，要另外核对。

当然，队列少了一张单，也不能证明下一位审批人选对了。还得回看留下的待办和审批记录。持续没有进展时，运行要能停下来，让人看见原因。

写到这里，Flow Runner 的位置反而清楚了一点。业务逻辑交给 Agent，并不意味着软件不用管执行过程。软件要把每次尝试和留下的事实记清楚，Agent 则拿着公司的规则继续办事。

我们希望哪天换掉 Pi，或者由客户自己的 Agent 接手，事情仍然能接着做。能交接的应该是工作本身，而不只是一段提示词。
